# deepdemos.top：从 AI Demo 作品库到模型能力数据库

> **核心愿景：**
>
> **deepdemos.top 不应该只是“AI 生成 Demo 的作品库”，而应该逐渐成为“从 Demo 观察模型能力的数据库”。**
>
> 作品是结果，Prompt 是任务描述，Model 是执行者，Task 是可比较的题目，Tag 是描述与导航工具。  
> 当这些信息被系统化连接起来，网站才会从“展示作品”进化成“观察模型能力”。

---

## 一、先确定产品到底是什么

deepdemos.top 表面上是一个 AI 生成 Demo 的分享站，但真正能够形成长期价值的，并不是 Demo 文件本身。

单个 Demo 的价值通常来自：

- 它做了什么
- 它是怎么做出来的
- 使用了什么模型
- 使用了什么 Prompt
- 和其他模型做同一件事情时表现如何
- 这个结果属于什么类型、使用了什么技术、体现了什么能力

因此，网站最终更适合被理解为：

> **一个以真实 AI 生成结果为样本，记录“模型 × 任务 × Prompt × 结果”的开放数据库。**

这会带来一个非常重要的产品转变：

### 传统 Demo Gallery

```text
用户
 ↓
上传 Demo
 ↓
展示 Demo
 ↓
别人点赞 / 浏览
```

### deepdemos 未来形态

```text
任务 Task
   ↓
Prompt
   ↓
Model
   ↓
Generation
   ↓
Demo
   ↓
能力 / 类型 / 技术 / 结果
   ↓
与其他模型横向比较
```

前者是在“收集作品”。

后者是在“积累数据”。

---

# 二、为什么“模型”应该从普通 Tag 中独立出来

当前最容易犯的错误，是把所有信息都看成 Tag：

```text
model:deepseek
type:game
tech:threejs
feature:3d
```

这种设计早期非常方便，因为实现简单、扩展性强。

但当网站真正开始积累大量数据之后，会发现：

> **模型和普通标签不是同一种东西。**

“3D”是一个属性。

“游戏”是一个分类。

“Three.js”是一个技术。

而“DeepSeek V4 Flash”是一个真正参与生成 Demo 的实体。

模型有自己的：

- 厂商
- 系列
- 版本
- 别名
- 发布状态
- 能力信息
- 与其他模型的关系

更重要的是：

> **模型会参与“比较”。**

所以 Model 应该逐渐成为一级对象。

---

# 三、推荐的核心概念模型

建议将网站核心概念收敛到五个对象：

```text
┌──────────┐
│  Model   │
└────┬─────┘
     │
     │ 执行
     ▼
┌──────────────┐
│ Generation   │
└──────┬───────┘
       │
       │ 产生
       ▼
┌──────────┐
│   Demo   │
└──────────┘

┌──────────┐
│   Task   │
└────┬─────┘
     │
     │ 描述要解决的问题
     ▼
   Prompt

Tag / Taxonomy
用于描述、分类、筛选和导航
```

可以把五者理解为：

| 对象 | 回答的问题 |
|---|---|
| **Task** | “要让 AI 完成什么事情？” |
| **Prompt** | “具体怎样要求 AI？” |
| **Model** | “是谁完成的？” |
| **Generation** | “这一次生成过程是什么？” |
| **Demo** | “最终结果是什么？” |
| **Tag / Taxonomy** | “这个结果还有哪些属性？” |

这里最重要的一点是：

> **Tag 不再负责解释整个世界。**

---

# 四、Task：比 Demo 更重要的“题目”

这是未来最值得建设的概念之一。

比如一个用户上传了：

> “用 Three.js 做一个可以旋转、缩放的 3D 地球。”

这本身是一个 Prompt。

但从更高层看，它实际上属于：

```text
Task
└── 3D 地球可视化
```

以后另一个人可能输入：

> “制作一个 Web 端交互式地球仪，可以旋转查看不同国家。”

文字不同，但解决的是相近的问题。

因此可以把多个 Prompt 归并到同一个 Task。

---

# 五、为什么 Task 非常重要

没有 Task：

```text
DeepSeek Demo A
Qwen Demo B
Claude Demo C
```

它们只是三个作品。

有 Task：

```text
Task：3D 地球可视化

DeepSeek
 └── Demo A

Qwen
 └── Demo B

Claude
 └── Demo C
```

立刻就产生了“比较”的可能。

于是网站的核心单位从：

> 一个 Demo

变成：

> **一个任务下，不同模型产生的多个结果。**

这就是从作品库走向模型能力数据库的关键一步。

---

# 六、不要把 Task 完全依赖人工创建

最佳实践是：

> **Task 应该由系统辅助归并，而不是要求上传者自己精确选择 Task。**

原因很简单：

普通用户很难知道：

- 自己的 Prompt 属于哪个 Task
- 站内有没有相似 Task
- 应该新建还是复用
- 两个近似 Prompt 是否算同一道题

更合理的流程：

```text
用户提交 Prompt
      ↓
文本标准化
      ↓
相似 Prompt 检索
      ↓
给出候选 Task
      ↓
用户确认 / 系统自动归并
```

后期可以进一步使用 embedding / 语义相似度进行 Task 聚类。

但这里有一个最佳实践：

> **AI 可以负责“建议归类”，但不要在没有审查机制的情况下无限自动创建分类。**

否则很容易形成大量近义、碎片化 Task。

---

# 七、Generation：连接 Model 与 Demo 的关键

为什么不直接设计：

```text
Demo → Model
```

而推荐：

```text
Demo
 ↓
Generation
 ↓
Model
```

因为真实世界很快就会出现：

### 一个 Demo 使用多个模型

例如：

```text
Claude
负责设计

DeepSeek
负责代码

Qwen
负责调试
```

### 同一个 Demo 被不同模型重新生成

```text
Task：俄罗斯方块

Generation A
Model = DeepSeek
Prompt = P1
Result = Demo A

Generation B
Model = Qwen
Prompt = P2
Result = Demo B
```

### 同一模型多轮生成

```text
Generation
 ├── Prompt 1
 ├── Prompt 2
 ├── Prompt 3
 └── Final Demo
```

所以 Generation 是非常有价值的中间层。

---

# 八、最核心的关系

未来推荐形成：

```text
Task
  │
  ├──────── Prompt A
  │              │
  │              ▼
  │         Model A
  │              │
  │              ▼
  │           Demo A
  │
  ├──────── Prompt B
  │              │
  │              ▼
  │         Model B
  │              │
  │              ▼
  │           Demo B
  │
  └──────── Prompt C
                 │
                 ▼
            Model C
                 │
                 ▼
              Demo C
```

这实际上就是：

> **同一道题，多位选手作答。**

而 deepdemos 可以记录这些“作答结果”。

---

# 九、“同题模型对比”应该成为核心产品能力

这是整个产品最值得建设的方向之一。

例如：

## 任务：制作一个俄罗斯方块网页游戏

```text
┌─────────────────────────────────────────┐
│ 俄罗斯方块                               │
│                                         │
│ 共有 8 个模型完成过这个任务              │
│                                         │
│ DeepSeek V4 Flash     查看 Demo →       │
│ Qwen 3.8 Flash        查看 Demo →       │
│ Claude                  查看 Demo →       │
│ GPT                     查看 Demo →       │
└─────────────────────────────────────────┘
```

这里最关键的是：

> **不要急着给模型下一个“绝对强弱”的结论。**

网站更适合展示真实结果，让用户自己观察。

例如：

```text
任务：3D 地球

DeepSeek
- 完成度
- 视觉效果
- 交互
- 代码复杂度

Qwen
- 完成度
- 视觉效果
- 交互
- 代码复杂度

Claude
- 完成度
- 视觉效果
- 交互
- 代码复杂度
```

这样数据天然具有更高可信度。

---

# 十、“模型能力数据库”不等于“模型排行榜”

这一点非常重要。

不建议把产品简单做成：

```text
DeepSeek：93 分
Claude：91 分
Qwen：89 分
```

因为这种综合分非常容易产生误导：

- 任务不同
- Prompt 不同
- 用户不同
- 评判标准不同
- Demo 类型不同

最佳实践是：

> **优先记录事实，再提供对比；谨慎提供结论。**

可以观察：

```text
某模型在游戏类任务出现频率高

某模型在 3D Demo 中表现突出

某模型经常使用 Three.js

某模型在相同 Task 下生成结果更完整
```

这些属于“数据观察”。

比简单制造一个排行榜更有长期价值。

# 十一、模型主页

当 Model 成为一级对象之后，就应该拥有自己的主页。

例如：

# DeepSeek V4 Flash

```text
作品数
128

参与任务
47

涉及技术
Three.js / Canvas / WebGL / React ...

常见类型
游戏 / 可视化 / 工具 / 仿真 ...

━━━━━━━━━━━━━━━━━━

热门任务

俄罗斯方块
3D 地球
粒子系统
天气模拟
...
```

下面再进入：

```text
同题对比
```

这样模型主页就不再是简单的“筛选结果”。

它会变成：

> **这个模型在真实 Demo 世界里的行为档案。**

---

# 十二、模型能力应该从真实 Demo 数据中“长出来”

不建议一开始就人工定义：

```text
DeepSeek
游戏：★★★★★
3D：★★★★☆
Coding：★★★★★
```

这种体系很容易变成主观评价。

更好的做法：

```text
Demo 数据
    ↓
Task
    ↓
Category
    ↓
Technology
    ↓
Model
    ↓
统计 / 观察
```

例如系统发现：

```text
DeepSeek

游戏类 Demo：31
3D Demo：24
WebGL Demo：19
数据可视化：18
```

这就是客观的数据画像。

未来再考虑更高级的自动分析。

# 十三、Explore：不要把 /tags 做成“标签数据库页面”

用户真正需要的是：

> “我想探索这个站里有什么。”

而不是：

> “我想查看数据库里存在多少个 TagKey。”

因此未来的探索页可以：

```text
Explore

热门模型
DeepSeek
Qwen
Claude
GPT
...

热门类型
游戏
3D
工具
可视化
模拟
...

热门技术
Three.js
WebGL
Canvas
SVG
...

热门任务
俄罗斯方块
3D 地球
天气模拟
...
```

也就是说：

> `/tags` 最终更应该成为 `/explore`。

---

# 十四、模型、分类、技术、Task 应该分别成为导航入口

推荐最终形成：

```text
Explore
│
├── Models
│
├── Tasks
│
├── Categories
│
├── Technologies
└── Features
```

它们看起来都可以像“标签”，但语义完全不同。

这会让站点导航从：

> “搜索一堆标签”

升级成：

> **“从不同维度探索 AI 生成世界。”**

---

# 十五、Tag 仍然非常重要，但它应该退回正确的位置

Tag 并不是要被消灭。

恰恰相反，Tag 仍然是非常重要的基础设施。

但它更适合承担：

```text
描述
分类
筛选
搜索
相关推荐
```

而不应该承担：

```text
Model 身份
Prompt 身份
Task 身份
Generation 身份
```

可以理解为：

> **实体负责表达“是什么”，Tag 负责表达“有什么特征”。**

---

# 十六、标签系统的最佳实践：不要追求“标签越多越好”

一个常见误区：

```text
发现表达能力不够
↓
增加 500 个 Tag
↓
发现还是不够
↓
继续增加
```

最终结果往往是：

```text
标签越来越多
用户越来越不会选
标签越来越不统一
搜索效果越来越差
```

更好的原则：

> **优先建设结构，而不是建设数量。**

标签体系应该具备：

```text
Canonical Tag
Alias
Parent
Group
Related
Implication
Deprecated
```

例如：

```text
Three.js

别名：
threejs
three.js

上位概念：
Web Graphics

隐含属性：
3D
WebGL

相关：
Babylon.js
```

---

# 十七、标签应该允许“推导”

一个好的标签系统，不应该要求用户手工填写所有信息。

例如用户只选择：

```text
Three.js
```

系统可以自动推断：

```text
WebGL
3D
Web graphics
```

用户只需要提供最小信息，系统负责补充。

这种设计可以称为：

> **Minimal Input, Rich Metadata**

即：

> **用户输入尽可能少，系统形成的元数据尽可能丰富。**

这会直接降低上传成本。

---

# 十八、上传页面的最佳实践

上传者真正应该做的是：

> 告诉系统“这个 Demo 是什么”。

而不是：

> 帮数据库维护标签体系。

推荐：

```text
上传 Demo

① 选择 / 识别模型
② 输入 Prompt
③ 系统推荐标签
④ 用户确认
⑤ 可选手动补充
```

推荐标签应该优先出现。

例如：

```text
系统推荐

[DeepSeek V4 Flash]
[游戏]
[3D]
[Three.js]
[WebGL]
```

用户只需：

```text
全部接受
```

或者：

```text
删除一个
```

---

# 十九、AI 推荐标签的最佳实践

AI 自动打标签很适合这个项目，但不要让 AI 成为唯一真相。

推荐流程：

```text
Prompt
+
Demo 元数据
+
代码 / 技术分析
+
截图 / 结构分析
       ↓
   AI 推荐
       ↓
Canonical Tag
       ↓
用户确认 / 可信规则自动确认
```

同时把标签来源记录下来：

```text
source = user
source = ai
source = inferred
source = admin
```

这样后期出现错误时，可以知道这个标签是怎么来的。

这是长期维护非常重要的最佳实践。

---

# 二十、统一 Tag UI

标签相关 UI 最好只建立一套视觉语言。

推荐统一成现在你喜欢的：

> **青色边框 + 可折叠分组**

所有地方共享同一个 Group 组件。

例如：

```text
┌────────────────────────────────────┐
│ MODEL                         23   │
│                                    │
│ DeepSeek                           │
│ [V4 Flash] [V4 Pro] [R1]           │
│                                    │
│ Qwen                               │
│ [3.8 Flash] [Coder]                │
└────────────────────────────────────┘
```

在不同页面只改变行为：

```text
Upload
→ 选择

Filter
→ 筛选

Detail
→ 展示

Admin
→ 管理
```

而不是每个页面都有自己的 Tag UI。

---

# 二十一、同一 TagKey 内 OR，不同 TagKey 之间 AND

这是筛选系统非常重要的最佳实践。

例如用户选择：

```text
模型：
DeepSeek
Qwen

类型：
游戏
模拟

技术：
Three.js
```

应解释为：

```text
(DeepSeek OR Qwen)
AND
(游戏 OR 模拟)
AND
Three.js
```

而不是：

```text
DeepSeek
AND
Qwen
AND
游戏
AND
模拟
```

这样用户才能真正做多维检索。

---

# 二十二、模型应该具有更高的 UI 权重

这是符合用户认知的。

对于 Demo：

```text
模型
类型
Task
技术
Feature
```

重要程度并不相同。

其中：

> **Model 通常是用户最关心的元数据之一。**

因此可以在 Demo Card 上：

```text
┌──────────────────────────────┐
│      Demo Preview            │
│                              │
│ DeepSeek V4 Flash            │
│ 俄罗斯方块                    │
│                              │
│ [Game] [WebGL] [3D]          │
└──────────────────────────────┘
```

模型应该拥有稳定、醒目的识别位置。

而不是和几十个普通 Tag 平起平坐。

---

# 二十三、Demo 详情页应该出现“同题作品”

假设用户正在看：

```text
3D 地球 Demo
```

下面应该可以出现：

## 相同任务的其他实现

```text
DeepSeek
Qwen
Claude
GPT
```

这样用户不会因为看完一个 Demo 就结束浏览。

而是自然进入：

```text
Demo
 ↓
同题 Demo
 ↓
模型
 ↓
模型其他 Demo
 ↓
其他 Task
```

这会形成非常强的内部推荐网络。

---

# 二十四、最终的浏览路径应该变成一个图

用户可以从任意维度进入：

```text
          Model
            │
            ▼
           Demo
        ↙       ↘
      Task      Tags
       │          │
       ▼          ▼
   其他 Demo    其他 Demo
       │
       ▼
     Model
```

这意味着：

> **网站不是一个列表，而是一张“AI 生成作品关系图”。**

用户可以从：

```text
模型 → Demo → Task → 其他模型
```

也可以：

```text
Task → 模型 → Demo
```

甚至：

```text
技术 → Demo → Task → 模型
```

这会显著增加内容之间的连接密度。

---

# 二十五、产品最终应该沉淀三类数据

从长期来看，deepdemos 最珍贵的资产不是图片，也不是网页 Demo。

而是三类关系数据。

## 1. 模型做过什么

```text
Model → Demo
```

## 2. 模型在什么任务上做过什么

```text
Model → Task → Demo
```

## 3. 不同模型面对相同任务时产生了什么结果

```text
Task
 ├── Model A → Demo A
 ├── Model B → Demo B
 ├── Model C → Demo C
 └── Model D → Demo D
```

第三类数据的价值最高。

---

# 二十六、不要过早做“模型评分”

尤其不要在数据量还很小的时候做：

```text
综合能力：
★★★★★
```

更不建议：

```text
DeepSeek > Qwen > Claude
```

应该优先做到：

```text
样本数量足够
Task 定义稳定
Prompt 信息完整
模型身份可靠
Demo 可复现 / 可查看
```

之后才考虑：

```text
完成度
视觉效果
功能性
代码质量
稳定性
```

而且最好保持：

> **每个指标独立，而不是强行合并成一个总分。**

---

# 二十七、推荐的产品演进路线

## 阶段 1：把 Model 从 Tag 的视觉权重中提出来

暂时不重构数据库。

先做到：

```text
Demo Card
→ 明确显示 Model

Demo Detail
→ 明确显示 Model

Filter
→ Model 一级筛选

Explore
→ Model 一级入口
```

这是投入最小、收益最高的一步。

---

## 阶段 2：建立 Model 页面

实现：

```text
/models/deepseek-v4-flash
```

展示：

- Demo 数量
- Task 数量
- 类型分布
- 技术分布
- 最近作品
- 热门作品

这一步开始真正体现：

> “模型数据库”。

---

## 阶段 3：建立 Task

开始识别：

```text
相似 Prompt
↓
同一 Task
```

并建立：

```text
/tasks/tetris
/tasks/3d-earth
/tasks/weather-simulation
```

---

## 阶段 4：建立 Generation

将：

```text
Model
Prompt
Demo
```

关系正式结构化。

---

## 阶段 5：同题模型比较

加入：

```text
Same Task
↓
Multiple Models
↓
Multiple Results
```

这是最重要的产品能力。

---

## 阶段 6：模型能力观察

开始基于真实数据生成：

```text
模型画像
能力分布
任务覆盖
技术偏好
成功率 / 完成度
```

注意：

> 数据先于结论。

# 二十八、最佳实践总纲

整个项目可以长期遵循下面这几条原则。

### 原则 1：不要让 Tag 成为万能对象

```text
Model 是 Model
Task 是 Task
Generation 是 Generation
Tag 是 Tag
```

各司其职。

---

### 原则 2：用户维护最少，系统补充最多

用户不应该成为免费的数据库管理员。

应该：

```text
用户输入少量信息
↓
系统推荐
↓
系统推导
↓
用户确认
```

---

### 原则 3：优先标准化，再增加数量

宁愿：

```text
100 个高质量标准 Tag
```

也不要：

```text
1000 个互相重复的 Tag
```

---

### 原则 4：同维度 OR，跨维度 AND

这是多标签筛选最符合用户直觉的规则。

---

### 原则 5：模型是核心实体，而不是普通分类

因为模型不仅是标签。

它是：

> **Demo 的生成者。**

---

### 原则 6：不要急着评价模型，让数据自己说话

优先：

```text
记录
比较
统计
观察
```

再：

```text
评分
排名
结论
```

---

### 原则 7：AI 可以协助整理数据，但不应该成为不可控的真相源

任何自动标签、自动 Task 聚类、自动模型归类，都应该存在：

```text
来源
置信度
纠错
合并
废弃
```

机制。

---

### 原则 8：所有元数据都应该服务于“探索”

最终目的不是建立一个漂亮的数据库。

而是让用户更容易发现：

```text
这个 Demo 是什么？
谁做的？
用什么模型做的？
这个模型还能做什么？
别人做同一道题效果如何？
还有哪些类似任务？
```

如果一个字段无法帮助这些问题，它就不一定值得存在。

---

# 二十九、最终产品形态

最终希望用户看到的不是：

```text
Demo #1234
Tags:
model:x
type:y
tech:z
...
```

而是：

```text
┌─────────────────────────────────────────┐
│           俄罗斯方块                     │
│                                         │
│ Model                                   │
│ DeepSeek V4 Flash                       │
│                                         │
│ Task                                    │
│ 俄罗斯方块网页游戏                       │
│                                         │
│ Prompt                                  │
│ “制作一个可以直接游玩的俄罗斯方块……”     │
│                                         │
│ Technology                              │
│ Three.js · Canvas                       │
│                                         │
│ Tags                                    │
│ Game · 2D · Interactive                 │
└─────────────────────────────────────────┘

      查看同题模型
             ↓

┌─────────────────────────────────────────┐
│ DeepSeek      查看 Demo                  │
│ Qwen          查看 Demo                  │
│ Claude        查看 Demo                  │
│ GPT           查看 Demo                  │
└─────────────────────────────────────────┘
```

这时 deepdemos 的核心价值就发生了变化。

它不再只是：

> **“这里有很多 AI 做出来的 Demo。”**

而变成：

> **“这里记录了不同 AI 在真实任务上的实际表现。”**

---

# 三十、最终愿景

deepdemos.top 最值得建设的，不是一个更漂亮的 Demo Gallery。

而是一套持续增长的：

```text
AI Model
      ×
Task
      ×
Prompt
      ×
Generation
      ×
Demo
      ×
Metadata
```

关系数据库。

随着数据积累，用户最终可以回答很多有价值的问题：

> 哪些模型经常做游戏？

> 哪些模型擅长 3D？

> 同一个 Prompt 给不同模型，会产生什么差异？

> 同一个 Task，哪个模型更容易一次完成？

> 某个模型除了当前 Demo，还做过什么？

> 某种技术通常被哪些模型使用？

> 某类任务最近出现了哪些新的模型结果？

而这些问题，正是一个普通“作品展示站”无法自然回答的。

---

# 结语

**deepdemos.top 最终不应该只是“AI 生成 Demo 的作品库”，而应该逐渐成为“从 Demo 观察模型能力的数据库”。**

这个定位决定了后续设计的方向：

```text
Demo 是结果
Prompt 是过程的入口
Task 是比较单位
Model 是核心实体
Generation 是关系纽带
Tag 是描述与导航
```

最终形成：

```text
             Model
               │
               ▼
            Generation
          ↙           ↘
       Prompt          Demo
          │              │
          ▼              ▼
         Task ←────── Metadata
          │
          ▼
     同题模型比较
          │
          ▼
      模型能力观察
```

**不要从“怎样把标签做得更复杂”出发。**

应该从：

> **“我们未来希望用户能够比较、探索和理解什么？”**

反过来设计数据结构、标签体系、页面和交互。

这会让 deepdemos 的产品方向越来越清晰，也会避免在不断修补 Tag 系统的过程中把整个项目做成一个难以维护的“万能标签数据库”。
