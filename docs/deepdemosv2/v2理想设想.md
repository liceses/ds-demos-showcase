> 本文综合 `docs/deepdemosv2/` 下四份文档的核心观点：
> ① `Ai相关.md`（LLM 与算法分层）② `deepdemos_模型能力数据库_概念与最佳实践.md`（产品愿景）
> ③ `deepdemos_长期运营维护与知识治理方案.md`（治理体系）④ `建议2.md`（实体化与 Benchmark 定稿）

## 一、愿景：从作品库到模型能力数据库

**核心定位转变：**

> deepdemos.top 不应该只是「AI 生成 Demo 的作品库」，而应该逐渐成为「从 Demo 观察模型能力的数据库」。

- 作品是结果，Prompt 是任务描述，Model 是执行者，Task 是可比较的题目，Tag 是描述与导航工具。
- 当这些信息被系统化连接起来，网站才会从「展示作品」进化成「观察模型能力」。
- 单个 Demo 的价值来自：它做了什么、怎么做的、用了什么模型、什么 Prompt、与其他模型做同一件事时表现如何。

**传统 Demo Gallery：**

```text
用户 → 上传 Demo → 展示 Demo → 别人点赞/浏览
```

**DeepDemos 未来形态：**

```text
任务 Task → Prompt → Model → Generation → Demo → 能力/类型/技术/结果 → 与其他模型横向比较
```

前者是在「收集作品」，后者是在「积累数据」。

**与普通 Benchmark 的本质区别：**

> 普通 Benchmark：一个分数。
> DeepDemos：**一个可体验、可追溯、可比较的真实结果。**

## 二、核心概念模型

### 2.1 六实体

```text
                 MODEL
                   │
            ┌──────┴──────┐
            │             │
          TASK           ...
            │
         PROMPT
            │
           RUN
            │
          DEMO
            │
       Rating / Review
```

| 实体 | 回答的问题 |
|---|---|
| **Model** | 谁做的 |
| **Task** | 做什么（要 AI 完成什么事情） |
| **Prompt** | 怎么要求它做（具体怎样要求 AI） |
| **Run / Generation** | 怎么生成（一次具体生成过程） |
| **Demo** | 最终做出了什么（最终结果） |
| **Rating / Review** | 用户怎么看 |

### 2.2 关系

```text
Model ─────┐
           ↓
Task → Prompt → Run → Demo
```

- **Task**：比 Demo 更重要的「题目」。多个文字不同的 Prompt 可以归并到同一个 Task。
- **Prompt 不与 Task 混在一起**：同一 Task（如「制作 3D 黑洞模拟器」）可能有多个 Prompt（英文/指定技术栈/不同风格），不同 Prompt 产生不同结果。
- **Run 提前预留**：支持「第一次生成失败 → 第二次修改 Prompt → 第三次生成成功」的完整过程记录：

```text
Task #12
   ├── Run #1  Prompt A  ❌
   ├── Run #2  Prompt B  ⚠️
   └── Run #3  Prompt C  ✅ Demo
```

### 2.3 Tag 退位

> **Model / Task / Prompt / Run 不再是 Tag。**
> Tag 只负责：描述。Entity 负责：建立关系。

```text
Demo
 ├── model_id      → Model
 ├── task_id       → Task
 ├── prompt_id     → Prompt
 ├── run_id        → Run
 │
 └── tags
      ├── type
      ├── category
      ├── game
      ├── skills
      └── ...
```

### 2.4 实体与属性的判断标准

以后每增加一个新的知识概念，问五个问题：

1. 它是不是一个真正的实体？（是 → 独立，如 Model / Task）
2. 它是不是只是一个属性？（是 → Tag 即可）
3. 它是否需要自己的生命周期？（需要 → 必须拥有独立管理能力）
4. 它是否需要被比较？（需要 → 尽量独立建模）
5. 它是否会产生大量用户贡献？（会 → 进入 Candidate → Review → Canonical 治理链路）

## 三、数据关系与浏览路径

### 3.1 浏览路径变成一张图

```text
          Model
            │
            ▼
           Demo
        ↙       ↘
      Task      Tags
       │          │
       ▼          ▼
   其他 Demo    其他 Demo
       │
       ▼
     Model
```

用户可以从任意维度进入：

```text
Demo → Model → 其他 Demo → 共同 Task → Benchmark → 另一个 Model
```

### 3.2 同题作品

Demo 详情页应该出现「相同任务的其他实现」：

```text
Task：3D 地球可视化
DeepSeek → Demo A
Qwen     → Demo B
Claude   → Demo C
```

用户不会因为看完一个 Demo 就结束浏览，而是自然进入：Demo → 同题 Demo → 模型 → 模型其他 Demo → 其他 Task。

### 3.3 三类沉淀数据（按价值排序）

1. **模型做过什么**：`Model → Demo`
2. **模型在什么任务上做过什么**：`Model → Task → Demo`
3. **不同模型面对相同任务时产生了什么结果**：`Task → Model A → Demo A / Model B → Demo B / ...`（价值最高）

## 四、Benchmark 设想

### 4.1 定义

> **Benchmark = 对同一个 Task 下多个 Model/Run/Demo 的组织与比较。**

Benchmark 的本质是：**固定 Task，然后比较不同 Model。**

### 4.2 结构

```text
Task：制作一个在线国际象棋游戏

Model A  Prompt A → Run A → Demo A → 评分 4.7
Model B  Prompt B → Run B → Demo B → 评分 4.4
Model C  Prompt C → Run C → Demo C → 评分 4.8
```

Benchmark 页面自动得到：

```text
国际象棋游戏
Model A   4.7
Model B   4.4
Model C   4.8
```

用户还可以继续点：看 Demo、看 Prompt、看生成过程。

### 4.3 原则

- **不要急着给模型下「绝对强弱」的结论**：网站更适合展示真实结果，让用户自己观察。
- **优先记录事实，再提供对比；谨慎提供结论**。
- 可以观察「某模型在游戏类任务出现频率高」「某模型在相同 Task 下生成结果更完整」这类数据观察，比简单制造排行榜更有长期价值。
- 不建议做「综合能力 ★★★★★」或「DeepSeek > Qwen > Claude」这类结论。
- 每个指标独立，不强行合并成一个总分。

## 五、技术分层：规则 → 算法 → LLM → 人工

### 5.1 四层系统

```text
第一层：Deterministic Rules（最可靠、最便宜）
    字符串标准化 / Alias / Exact Match / 数据库约束 / 业务规则 / 黑名单 / 白名单

第二层：Statistical / ML Algorithms（负责大规模计算）
    Embedding / Similarity / Clustering / Ranking / Anomaly Detection

第三层：LLM（负责复杂语义）
    Semantic Classification / Task Understanding / Tag Recommendation
    Duplicate Reasoning / Entity Resolution / Natural Language Explanation

第四层：Human Governance（负责最终边界）
    Canonical / Merge / Taxonomy / 规则 / 重大变更 / 争议处理
```

### 5.2 分工原则

> **能用规则解决的，不用算法；能用算法解决的，不用 LLM；能让 LLM 给建议的，不让 LLM 直接决定；能自动处理的，不交给管理员手工处理。**

| 功能 | LLM | 算法 | 人工 |
|---|:--:|:--:|:--:|
| 标签字符串标准化 | ❌ | ✅ | ❌ |
| Alias 匹配 | ❌ | ✅ | 可选 |
| Model 精确匹配 | ❌ | ✅ | ❌ |
| Model 疑似重复判断 | ✅ | ✅ | ✅ |
| Prompt 相似检索 | ❌ | ✅ | ❌ |
| Task 聚类候选 | 辅助 | ✅ | ✅ |
| Task 命名 | ✅ | ❌ | ✅ |
| Tag 推荐 | ✅ | ✅ | 可选 |
| 技术栈识别 | ✅ | ✅ | 可选 |
| Demo 类型识别 | ✅ | ✅ | 可选 |
| 重大 Taxonomy 修改 | ❌ | ❌ | ✅ |
| 数据统计 | ❌ | ✅ | ❌ |
| 异常检测 | 可辅助 | ✅ | 可选 |
| 最终 Canonical 决定 | ❌ | ❌ | ✅ |

### 5.3 不要让 LLM 成为数据真相

LLM 说「这个 Demo 使用了 WebGL」不能直接写入数据库，应该：

```text
Inference
technology = WebGL
confidence = 0.94
source = llm
status = suggested
```

管理员确认后：`status = verified`。

### 5.4 术语建议

- 不写「AI 自动推荐标签」，写 **LLM-assisted Tag Recommendation**
- 不写「AI 自动 Task 聚类」，写 **Embedding-based Task Retrieval + LLM-assisted Clustering**
- 产品文档统一使用：`LLM`（语义理解）、`ML / Algorithm`（embedding/聚类/相似度）、`Knowledge Engine`（两者 + 规则 + 数据库 + 审核系统）

## 六、标签系统演进

### 6.1 标签最佳实践

标签体系应该具备：

```text
Canonical Tag / Alias / Parent / Group / Related / Implication / Deprecated
```

例如：

```text
Three.js
别名：threejs / three.js
上位概念：Web Graphics
隐含属性：3D / WebGL
相关：Babylon.js
```

### 6.2 标签推导（Minimal Input, Rich Metadata）

用户只选择 `Three.js`，系统自动推断 `WebGL / 3D / Web graphics`。

> 用户输入尽可能少，系统形成的元数据尽可能丰富。

### 6.3 筛选规则

**同一 TagKey 内 OR，不同 TagKey 之间 AND：**

```text
(DeepSeek OR Qwen) AND (游戏 OR 模拟) AND Three.js
```

### 6.4 Model 的 UI 权重

Model 通常是用户最关心的元数据，应该拥有稳定、醒目的识别位置，而不是和几十个普通 Tag 平起平坐：

```text
┌──────────────────────────────┐
│      Demo Preview            │
│ DeepSeek V4 Flash            │
│ 俄罗斯方块                    │
│ [Game] [WebGL] [3D]          │
└──────────────────────────────┘
```

### 6.5 TagKey Policy

每个 TagKey 定义「治理策略」：

```text
TagKeyPolicy
creation_mode / selection_mode / approval_required / max_values
allow_alias / allow_parent / allow_ai_create
show_on_upload / show_on_filter / show_on_card
```

不同维度的知识，不应该用同一套运营规则：

```text
Model      → 必须标准化，禁止自由创建，自动匹配，管理员确认新值
Category   → 严格控制层级，不允许用户自由创建一级分类
Technology → 半开放，支持 Alias，支持 AI 推荐
Feature    → 相对开放，可以批量合并
```

### 6.6 不要追求「标签越多越好」

优先建设结构，而不是建设数量：

```text
100 个高质量标准 Tag  >  1000 个互相重复的 Tag
```

## 七、治理体系

### 7.1 八条运营原则

1. **管理对象不是「标签」，而是「知识体系」**（Model/Task/Taxonomy/Technology/Feature/Tag/Prompt/Generation/Demo/Alias/Relation）
2. **「创建」和「维护」分离**：普通用户贡献候选，管理员审核/合并/归一化/批准/拒绝/废弃
3. **自动化发现，人工做边界判断**：AI 负责提高运营效率，人负责决定知识体系的边界
4. **能合并就不要创建新的**：「发现重复」放在「创建新标签」之前
5. **废弃而不是删除**：任何被使用过的实体都不应物理删除，用 `active/deprecated/merged/hidden` 状态管理
6. **任何自动变化都应该可追溯**：谁改的/什么时候/改了什么/为什么/来源/修改前后
7. **「知识体系稳定」比「标签数量丰富」更重要**：KPI 用重复率/孤立率/错误率/审核积压/搜索命中率/AI 采纳率，不用 Tag Count
8. **从第一天开始考虑迁移**：批量/搜索/过滤/导入/导出/合并/回滚/审计

### 7.2 Knowledge Center

```text
知识中心
├── 总览 Dashboard
├── 待处理 Inbox
│   ├── 新模型 / 新标签 / 新 Task / AI 建议 / 重复项 / 冲突项 / 低质量数据
├── Models / Tasks / Taxonomy / Tags / Relations / Generations
└── Audit Log
```

管理员打开后台，第一眼应该看到「待处理队列」而不是数据表：

```text
待处理：37
新模型 3 / 重复模型建议 5 / 新标签 12 / 疑似重复标签 7 / Task 合并建议 4 / 错误关联 2 / AI 低置信度推荐 4
```

### 7.3 实体生命周期

```text
Model:  discovered → candidate → verified → active → deprecated → archived
Task:   candidate → active → merged → split → deprecated
Tag:    suggested → active → deprecated → merged → hidden
```

- **观察期**：新建实体先 `candidate`，使用次数 > N 或管理员确认后升级 `active`，防止低价值实体污染主体系。
- **低频不等于无价值**：`count < 3 → delete` 是错的，应结合语义价值/是否核心分类/未来潜力判断。

### 7.4 Canonical + Alias

每一种核心实体都必须有规范实体，所有别名/错别字/旧名称/厂商叫法都指向 Canonical：

```text
Canonical: DeepSeek V4 Flash
Aliases: DeepSeek-V4-Flash / deepseek v4 flash / DS V4 Flash
```

系统内部永远使用 `canonical_id`，展示层显示 `display_name`。

**Alias 管理中心**：待确认列表（`threejs → three.js`、`ds-v4 → DeepSeek V4`），管理员确认/修改/拒绝。

### 7.5 Relations

统一抽象 `EntityRelation`：

```text
relation_type / source_id / target_id / confidence / source / created_by
```

第一阶段只支持少量高价值关系：`alias_of / merged_into / parent_of / related_to / implies`。不要一开始建设几十种 relation。

### 7.6 AI 推荐分级与安全边界

**按置信度分级：**

```text
高置信度（99%，标准别名）→ 自动接受，但保留日志
中置信度（87%，疑似属于 Task X）→ 管理员待审核
低置信度（54%，可能属于 3D）→ 记录，等待更多数据，不骚扰管理员
```

**AI 可以自动做：** 标准化大小写/去空格/Alias 建议/重复检测/推荐 Tag/Task/Model/统计/异常检测

**AI 默认不能自动做：** 删除实体/改变 Canonical/删除大量关联/移动顶级分类/合并大量历史数据/改变核心 taxonomy

### 7.7 数据质量巡检

系统每天/每周自动跑质量任务：

```text
缺失 Model / 缺失 Category / Task 孤立 / 过时 Model / 重复 Tag
无效 Alias / 孤立 Tag / 过多 Tag 的 Demo / 从未被使用的 Tag / 高频但未标准化的 Tag
```

**质量指标：** Tag Coverage（Model 97% / Type 94% / Technology 72% / Task 61%）、Duplicate Rate、AI Suggest Acceptance。

### 7.8 审计与变更管理

- **变更日志**：`Change #1842 { Type: Tag Merge, Before/After, Affected: 184 Demos, Operator, Reason, Time }`
- **Taxonomy 版本化**：结构性修改 v1 → v2，记录 change reason / changed nodes / migration result / operator / timestamp
- **重要变更发布机制**：Draft → Review → Approve → Publish
- **批量操作 Preview + Rollback**：Operation ID / Before Snapshot / After Snapshot / Operator / Timestamp
- **数据库备份不是唯一安全措施**：备份 + 操作日志 + 变更快照 + Migration + Rollback
- **所有知识变更通过 Service 层**：`merge_tag() / merge_model() / merge_task() / deprecate_tag() / publish_taxonomy() / accept_suggestion()`，Admin UI / API / AI Worker / Migration Script 都走相同业务规则

### 7.9 角色分权

```text
Super Admin        Taxonomy / Model / 系统配置 / 危险操作
Knowledge Editor   Tag / Model / Task / Alias / Relations
Moderator          Demo / 举报 / 用户提交 / 内容质量
Analyst            只读：Dashboard / 统计 / 模型能力数据 / 运营报告
```

危险操作统一二次确认；大规模操作要求 Preview → Confirm。

### 7.10 运营节奏

```text
每天    处理新模型/用户纠错/高置信度重复 → Inbox 不长期积压
每周    Task 聚类 / Tag 重复 / 模型 Alias / 低质量数据 / AI 推荐准确率 → Weekly Knowledge Report
每月    Taxonomy Review / Model Review / 热门 Task Review / 长尾 Tag Review
每季度  知识体系版本升级 + 数据库审计 + 索引检查 + 历史数据清洗 + 备份恢复演练 + 规则复盘
```

### 7.11 三个后台中心

```text
Knowledge Center   维护 Model/Task/Tag/Taxonomy/Relation/Alias
Operations Center  处理审核/纠错/举报/AI 建议/质量问题/批处理
Analytics Center   观察模型表现/Task 分布/标签覆盖/用户行为/搜索/推荐/数据质量
```

形成闭环：知识建设 → 运营维护 → 数据反馈 → 知识体系优化。

### 7.12 三个「千万不要」

1. **不要让管理员直接面对全部实体**（正确：今天需要处理 12 个问题）
2. **不要让 AI 直接修改 Canonical**（AI 建议「A 可能是 B，置信度 96%」，管理员确认）
3. **不要为了「完整」不断扩大 Taxonomy**（体系应该足够表达实际 Demo 且能稳定维护，不是把整个互联网分类完）

## 八、前端体验

### 8.1 前台轻量原则

> **后台数据结构可以升级得比较彻底，前台 UI 却可以保持现在的轻量风格。**

不需要：模型能力雷达 / Token 成本曲线 / SOTA 排名 / 性能指数 / 复杂折线图。

### 8.2 Demo Card

```text
DEEPSEEK V4

黑洞模拟器

3D · 仿真

★ 4.7   👁 812
```

点击 Model 名 → Model 页面；点击标题/Task → Task / Benchmark 页面。

### 8.3 Model 页面（轻）

```text
DeepSeek V4
18 Demos · 7 Tasks · 4.6 Community Score
最近作品 [Demo] [Demo] [Demo]
参与过的 Benchmark [Task] [Task] [Task]
```

### 8.4 Explore 页

`/tags` 最终应该成为 `/explore`：

```text
Explore
├── Models（热门模型：DeepSeek/Qwen/Claude/GPT）
├── Tasks（热门任务：俄罗斯方块/3D 地球/天气模拟）
├── Categories
├── Technologies（热门技术：Three.js/WebGL/Canvas/SVG）
└── Features
```

用户需要的是「我想探索这个站里有什么」，而不是「我想查看数据库里存在多少个 TagKey」。

### 8.5 上传流程

上传者真正应该做的是「告诉系统这个 Demo 是什么」，而不是「帮数据库维护标签体系」：

```text
① 选择/识别模型 → ② 输入 Prompt → ③ 系统推荐标签 → ④ 用户确认 → ⑤ 可选手动补充
```

推荐标签优先出现，用户只需「全部接受」或「删除一个」。

## 九、ds-unknown 与历史数据处理

### 9.1 Known / Unknown 分离

不把 `model:ds-unknown` 继续当作普通 Model Entity，而是区分：

```text
Model
├── Known Model
│   ├── DeepSeek V4 / Claude Opus 5 / HY4 / GLM ...
└── Unknown / Unverified Model
    └── 灰测模型
```

大量灰测 Demo 仍然可以正常进入系统。

### 9.2 映射更新机制

模型被确认后：

```text
ds-unknown → 确认 → DeepSeek V4 Preview
```

**只需要更新 Model Entity 的映射，而不是修改全部 Demo**——这对 367 个 ds-unknown 特别重要。

### 9.3 模型创建尽量自动完成

用户上传 `model: deepseek-v4-flash`，系统发现数据库已有 `DeepSeek V4 Flash` → 自动匹配直接关联，不重复创建；匹配不到 → 产生「新模型候选」进入管理员 Inbox。

**模型重复检测三层：** 精确匹配（canonical name/external id）→ Alias 匹配（deepseek-v4-flash / DeepSeek V4 Flash / ds-v4-flash）→ 语义匹配（AI 判断「95% 疑似重复」，管理员只需合并）。

## 十、分阶段演进

### 10.1 架构先建立，功能慢慢长

> 架构可以先建立，功能可以慢慢长。

**现在只需要真正落地：**

```text
Model Entity
Task Entity
Demo ↔ Model
Demo ↔ Task
```

**Prompt / Run 先保持现有系统兼容，以后再补。**

这样既不会过度设计，又不会把以后 Benchmark 的路堵死。

### 10.2 产品演进路线

```text
阶段 1：把 Model 从 Tag 的视觉权重中提出来（Demo Card/详情/筛选/Explore 明确显示 Model）
阶段 2：建立 Model 页面（/models/deepseek-v4-flash：Demo 数/Task 数/类型分布/技术分布/最近作品/热门作品）
阶段 3：建立 Task（相似 Prompt → 同一 Task，/tasks/tetris、/tasks/3d-earth）
阶段 4：建立 Generation（Model/Prompt/Demo 关系正式结构化）
阶段 5：同题模型比较（Same Task → Multiple Models → Multiple Results）
阶段 6：模型能力观察（基于真实数据生成模型画像/能力分布/任务覆盖/技术偏好）
```

### 10.3 治理体系实施顺序

```text
Phase 1：治理基础（Entity Status / Canonical / Alias / Audit Log / Inbox）——最重要的底座
Phase 2：Model 治理（Model Entity / Alias / Candidate / Merge / Detail）
Phase 3：Tag 治理（Tag Policy / Canonical Tag / Alias / Merge / Deprecated / Relation）
Phase 4：Task 治理（Task Candidate / Similarity / Cluster / Merge / Split / Detail）
Phase 5：AI 运营（AI Tag Suggestion / Model Matching / Task Matching / Duplicate Detection / Quality Scan）
Phase 6：知识体系版本化（Taxonomy Version / Draft / Review / Publish / Rollback）
Phase 7：模型能力数据层（Model Profile / Task Comparison / Capability Statistics / Model × Task Matrix）
```

产品价值在数据基础成熟后自然生长出来，而不是先做一个漂亮但空洞的排行榜。

## 十一、最终愿景

### 11.1 知识闭环

```text
              Knowledge Center
                    │
        ┌───────────┼───────────┐
        │           │           │
      Model        Task        Taxonomy
        │           │           │
      Alias       Prompt       Tag
        │           │           │
        └───────────┼───────────┘
                    │
                 Relation
                    │
                    ▼
                  Demo
                    │
                    ▼
              Generation
                    │
                    ▼
               Real Data
                    │
                    ▼
                Analytics
                    │
                    ▼
             Knowledge Improve
```

> **内容产生知识，知识组织内容，数据反过来改善知识。**

### 11.2 长期数据流

```text
用户上传 → 系统解析 → Model 匹配 → Prompt 分析 → Task 推荐 → Tag 推荐
→ Relations 推导 → 用户确认 → Demo 发布 → Knowledge Inbox → AI 质量巡检
→ 管理员处理异常 → 知识体系更新 → 统计 / Explore / Model Page
```

### 11.3 目标不是「自动化一切」

理想状态不是「AI 全自动管理网站」，而是：

> **Demo 增长 10 倍，人工工作量只增加 2～3 倍。**

机器处理重复工作，管理员处理判断工作。

### 11.4 一句话制度

> **用户负责贡献，AI 负责发现，系统负责归一化与执行，管理员负责判断，Taxonomy 负责稳定边界，Audit 负责追溯，Analytics 负责反馈。**
>
> **不要让管理员维护数据；要让管理员维护规则。**
