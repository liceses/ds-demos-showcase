# 优化设计：模型页可见性 · 卡片署名 · 社区分算法 · 后台信息架构

日期：2026-08-31 ｜ 状态：**第 1、2、3 条已实现并实测**；第 4 条（后台）见 `后台重设计.md`（第 1 期壳层已落地）
四条诉求里有三条同源，先给诊断，再逐条给方案与取舍。

> **决策人拍板后的实现回填**：① 卡片署名用**轻 chip**（去印章、去描边重量、挪到标题下方，兜底位不给链接）；② 社区分用经验贝叶斯收缩，**demo 数不进分数**，只并列票数 + 样本可信度档；③ 收缩强度 `m = 全站模型票数中位数`（真实语料实测 **m=15、C=4.4078**）；④ 模型页作品默认 `newest`，排序（最新/社区分/最热）与类型 facet 可切换并**写进 URL**；⑤ 分页端点 `GET /models/{slug}/demos`，首屏 12、每次再加载 24。
> 真实语料效果：`1 票 raw 5.0 → score 4.44`（被拉回先验），`77 票 raw 4.66 → 4.66` 稳居前列 —— 旧口径下前者会压过后者，这正是要修的缺陷。

## 0. 诊断：三条是同一个病灶，一条是另一类

| 反馈 | 代码事实 | 归类 |
|---|---|---|
| ① 模型页只能看到前十几个 demo | `recent_demos(limit=12)` 硬编码，只按 `created_at desc`；`ModelDetailOut.recent_demos` 一次下发 | 数据层没问题，**展示层截断** |
| ② 卡片 model chip 太突兀 | 卡片里 `ModelChips` 带 **EntityStamp（斜角印章）+ 描边 chip**，且独占一行**放在标题之上** | **语义想说"一等公民"，视觉用了档案页的语汇** → 层级倒置 |
| ③ 社区分没考虑 demo 数等因素 | `_agg_subqueries` 用 `AVG(Demo.rating_avg)` | **等权平均 + 平均的平均**：1 票的 5.0 与 40 票的 4.6 同权 |
| ④ 后台值得重做 | 16 面板 / 6 组 / 顶部两组横向 chips，默认落「审核队列」 | 信息架构是**增量堆积**，不是按任务组织 |

①②③ 的共同问题：**"模型"被提为一等实体，但展示层与统计层没跟上。** 这是 B1 之后一直欠的账。

## 1. 模型页作品可见性

**现状量化**：`ds-unknown` 396 件、`dsv4-pro` 34 件，页面固定 12 件 → 最大那个模型只能看到 **3%** 的作品。

### 方案对比

| 方案 | 做法 | 评价 |
|---|---|---|
**A. 首屏 12 + 分页端点** | `GET /models/{slug}/demos?page=&sort=&type=&game=` | ✅ **推荐**：首屏不劣化、渐进加载、可分享位置 |
B. 一次下发全部，前端切页 | 396 件 × 序列化（≈1.5KB/件） | ❌ 首屏 500KB+，序列化 CPU 与 SQL 都爆 |
C. 无限滚动 | IntersectionObserver | ❌ 与"我要找某个作品"的意图冲突：无限流没有终点、无法分享"我看到第 40 件"、也拿不到"到底了"的完成感 |

### 细节

- **排序**：`newest`（默认，保持现状语义）· `score`（社区口碑，依赖 §3 的新分数）· `popular`（view+download）
- **筛选（facet）**：用模型详情页已有的 `type_dist` / `game_dist` 作为可点筛选项 —— 数据现成，不新增查询；语义正好回答"这个模型擅长做什么"
- **分页交互**：按钮「再显示 24 件」+ 计数行「已显示 36 / 396」；到底显示"到底了"并给"按分数重排"的引导（避免长列表尽头的无力感）
- **深链**：`?page=2&sort=score` 写进 URL（可分享、浏览器后退可用）
- **性能预算**：每页 24 件走 `preload_demo_relations`（实测 page_size=20/100 都恒定 8 条 SQL）→ 新增 1 条 count + 1 条分页查询 ≈ 10 条，可接受
- **astra**：`/models` 前缀本就 404，子路由同样不可见（白名单制，**无需新增 DENY**）

## 2. 卡片上的模型署名（不是档案章）

**原则**：卡片的主任务是"这是什么作品" → **标题必须是卡片上对比度最高的元素**。印章/徽章是"档案"语汇，属于详情页与模型页。

### 方案对比

| 方案 | 做法 | 取舍 |
|---|---|---|
**① 标题下方署名行** | `由 dsv4-flash、HY4 等 3 个` 纯文字链接，放在描述之后、stats 之前 | ✅ **推荐**：层级正确、密度低、可点、多模型自然折叠 |
② 轻 chip（去印章去描边） | 浅底 + 厂商色小圆点 | ①的加强版；两张卡并排时仍会显挤 |
③ 只留首字母印章 | 极省空间 | ❌ 识别依赖记忆（违反"识别优于回忆"），中文厂商首字母无意义 |

### 四条细节规则

1. **语义前缀「由 …」**：把"这是署名/出处"讲明（provenance 明示），不是一个装饰标签
2. **多模型**：≤2 全列，>2 折叠为 `等 N 个`，完整名单放 `title` 悬浮
3. **兜底位弱化**：`未标注 / 未定型号` 用灰字，**且不给链接** —— 不给作者一条"点进去看一个空概念"的死路；`灰测未证实` 保留链接但去掉高对比描边
4. **可访问性**：署名是真实链接（键盘可达）；"是否兜底"不只靠颜色表达（已有文字）

**代价与对策**：卡片会少一个视觉锚点。若担心模型维度存在感下降 → 详情页与模型页保留印章（那里合理），作品库筛选条继续提供 model facet。这恰好就是 D5 说的"面板级 vs 行内分层"，不是例外。

## 3. 社区分算法（这是统计问题，不是样式问题）

### 现在的算法有什么错

```
score = AVG(demo.rating_avg)  WHERE demo.rating_count > 0
```
- **(a) 等权平均**：1 票作品与 40 票作品同权 → 单件高分作品可把模型顶上第一
- **(b) 平均的平均**：忽略了每件作品票数不同（样本量不等）
- **(c) 无样本表达**：读者无法判断这个分能不能信

### 建议：经验贝叶斯收缩（IMDB weighted rating 同族，无新数据需求）

```
score = v/(v+m) · R + m/(v+m) · C

R = Σ(demo.rating_avg × demo.rating_count) / Σ demo.rating_count   ← 按票数加权（修 b）
v = Σ demo.rating_count                                            ← 该模型收到的总票数
C = 全站按票数加权的整体均分（先验）
m = 全站模型票数的中位数（收缩强度，自适应）
```
性质：样本少 → 拉回全站平均；样本多 → 逼近自身真实分。可解释、无黑箱调参。

### demo 数怎么办（决策人提的"等其他因素"）

**不把 demo 数乘进分数。** 那等于宣布"多产 = 好用"，同一模型刷 50 件草稿就能上位 —— 是治理污染，不是统计。

改为**三元组并列 + 可信度标签**：

```
score 4.62（高样本）   ·   412 票   ·   34 件作品
score 4.90（低样本）   ·    6 票    ·    2 件作品   ← 一眼知道别当真
```
- 样本可信度：`v < 10` 低 · `10–49` 中 · `≥ 50` 高（阈值可调，写死在常量里而非散落各页）
- 排序：列表与 `/explore` 热门默认按 `score`，同分按 `v`；保留 `demos`（最活跃）、`new`、`name`

### 明确不做的三件事（避免过度设计）

1. **Benchmark 对比行（单个题目内）不做收缩** —— 题内样本本来就小，收缩会把"这次它确实更强"抹平；那里 `avg_rating` 保持原样并显示票数
2. **不做按作者去重的加权**（防刷票）：先**暴露信号**（v 与作品数）而不引入不透明的惩罚项；若将来出现真实刷票，再做 `v = distinct authors` 版本
3. **不做时间衰减**：模型能力会变，但"历史最好成绩"也有价值；要区分就先加"近 90 分"副指标，不混进主分

### 落地位置（单一来源）

- `model_service` 的聚合处一次算出 `R/v/C/m`，`_model_out` 新增 `score`、`votes`、`sample_level`；**保留 `rating_avg` 原语义**（重命名为 raw 均分含义，前端改显 `score`）→ 契约向后兼容，旧字段不改语义
- 列表排序、`/explore`、模型页、同题对比的"排序"统一取 `score`

## 4. 管理后台信息架构

### 任务分析（决定 IA，而不是按"我们有哪些接口"排面板）

| 频率 | 后台在做什么 | 现状 |
|---|---|---|
每天 | 看有什么**待办** → 清掉（审核 / 收件箱 / 巡检生成候选 / 题目候选成题） | 只有"审核队列"这一个队列可见，其余要靠导航记忆 |
每周 | 治理：细分、归属、合并、别名 + 看趋势 | 面板散在 6 个组里，没有"从异常跳到带过滤的处理页"的路径 |
偶尔 | 配置（设置 / 公告 / 用户） | 与高频操作混在同一层导航里 |

**结论：后台的主任务是"待办驱动的队列控制台"**，现在的首屏却是一个具体队列。

### ① 新增「概览台」为默认页

- **待办卡（带真实计数，点击直达）**：待审 demo · 收件箱 pending（按 kind 细分）· 巡检可处理项 · 题目候选簇 · 待归属兜底作品 · 未确认 candidate 模型
- **覆盖率快照**：model / type 覆盖 + 重复 slug（最要紧的三个数）
- **最近 8 条审计** + 一键进审计面板（"谁在动什么"是后台的呼吸）

### ② 导航：顶部两级横条 → **左侧栏两级 + 面板搜索**

- 侧栏：组 → 面板，**带计数徽章**（待办可见 = 不用记）
- 顶部搜索框按名称/关键词过滤面板，支持 `↑↓ + Enter` 跳转（后台面板还会增长；横条是线性扩展，侧栏是对数扩展）
- 窄屏折叠为顶部下拉，现有横向条退化为二级
- 内容区限最大宽度 + 单列滚动（宽屏下表格被拉满是"看着能扫，实际扫不动"）

### ③ 统一操作语言（跨面板一致性，最容易被忽略但最省钱）

写操作一律 **预览影响面 → 二次确认 → 结果回执（含审计说明）**。动词归一：

| 现在各面板的写法 | 统一为 |
|---|---|
| 批准 / 收下 / 采纳 / 一键成题 | **批准**（题目候选：批准后成题，写清"成题"这个结果） |
| 生成候选 / 放入收件箱 | **生成候选** |
| 执行 / 执行合并 / 应用 | **执行** |
| 驳回 / 不用了 / 丢弃 | **驳回**（表单里的"不用了"保持口语，但动作语义同类） |
| 预览 / 预览影响 / 预览撤销 | **预览影响** |

另：所有列表统一「筛选在上、分页在下、空态写清下一步做什么」。

### ④ 分期（避免一次大爆炸）

| 期 | 内容 | 风险 |
|---|---|---|
**第 1 期** | 概览台 + 侧栏导航（含徽章）——**只动壳层**，16 个面板原样挂载 | 低，收益立现 |
第 2 期 | 操作语言与确认文案统一、各面板空态/分页规范 | 中（面广，逐个改） |
第 3 期 | 概览台异常 → 带过滤参数直达面板（如 `低覆盖` 点进收件箱并预置 kind 筛选） | 低，依赖前两步 |

## 5. 验收标准（怎样算做对了，可测）

1. **模型页**：`ds-unknown` 的 396 件从"可见 3%" → 全部可达；首屏 SQL ≤ 10 条、TTFB 不劣化
2. **卡片**：标题是卡片内对比度最高元素；署名不再位于标题之上；无链接兜底位
3. **社区分**：构造用例锁死 —— 「1 件作品 / 1 票 / 5.0」的模型，`score` **必须低于**「12 件 / 40 票 / 4.7」的模型；且前者带"低样本"标签
4. **后台**：默认页一眼看到"有哪几个队列、各多少待办"；键盘 ≤ 2 次操作到达任意面板；同一动作在任意面板动词一致
