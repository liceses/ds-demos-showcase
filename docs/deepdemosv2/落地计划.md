## 1. 目标与范围

**一句话**：把站点从「AI 生成 Demo 的作品库」升级为「从 Demo 观察模型能力的数据库」——
Model / Task / Prompt 从 Tag 升格为实体，建立 `Task → Prompt → Run → Demo` 关系链，
同题对比（Benchmark = 固定 Task 比较多 Model）自然涌现。

**范围边界**：
- 不做：模型能力雷达图、Token 成本曲线、SOTA 综合排名、复杂图表（文档红线）。
- 不换基础设施：仍是 FastAPI + SQLite + 现有部署拓扑；不引入向量库 / 消息队列 / 新存储。
- 不破坏：现有 tag 筛选 URL、agent 上传指南、API 契约向后兼容（新字段只增不改）。

## 4. 标签系统专项治理（五问题 → 方案）

> 现状五问题：① 不好管理 ② 上传时不好选 ③ 分类查找没发挥 + 覆盖不足 ④ 视图混乱 ⑤ 重要性未分层。
> 五者同源：体系缺「**分层、覆盖率、一致性**」三件事。

### 4.1 问题 1 不好管理 → 巡检 + 一键修复（Inbox 模式）
- 管理后台新增「知识治理」Section，首屏 = **体检面板**（§3.2 覆盖率表即第一个组件），每行可点进「缺此键的 demo 列表」，支持批量补标（规则建议 + 一键应用 + 审计落笔）。
- 自动巡检进收件箱：孤立标签（0 引用）、相似标签（TF-IDF 规则层）、缺 description 的 fixed 值。

### 4.2 问题 2 上传不好选 → 两段式 + 标签推导 + 只强制一个
- 弹窗按 **Tier 分层**重排（§4.5）：第一屏只问「哪个模型做的」（必选，chips 搜索）；第二屏给**建议包**——规则推导「检测到游戏类 → 建议 game:我的世界 + type:game + category:仿真 [全收][逐个看]」，全可跳过。
- 标签推导 = 概念文档「Minimal Input, Rich Metadata」的直译：`game:X → type:game`、3D 类 category 联动等映射表；前端映射表 + 后端 `matching_service`（prompt 关键词）双通道。
- 认知负荷从「160 个值里挑 3 个」降到「确认 2 次」。
- **实现进度（2026-08-31，含一次判断更正）**：✅ **Tier 驱动**（选择器按 tier 排序、默认落在核心键、tier1 标「必选」、`TagKeyInfo.tier` 前端已消费）；✅ **标签推导建议包**（`POST /tags/derive` 匿名只读，规则见 `API_CONTRACT.md` §22）；✅ **整页三步向导已做**（设计依据见 `docs/deepdemosv2/上传页重设计.md`）：类型三张大卡（选项全可见 + 大命中区）、模型步把 Q2 四档断言做成**四个并列可见出口**（精确搜索 / 厂商族 / 未标注 / 灰测 —— 兜底与精确同层级）、第三步标题·描述·提示词·建议包·封面 + `高级` 折叠做受众分离、第四步**核对页**；配套**完成度仪表盘**（必答/建议/可选三层，点击直达）、校验**前移为步内门禁**（下一步禁用 + 就地说明，而非提交后弹错）、脏状态离开二次确认、切步焦点跟随与 `aria-current` / `prefers-reduced-motion`。
  > **更正**：我上一轮把「整页向导」判为收益递减而只做抽屉内引导。事实是 —— 12 个字段仍平铺、必答与可选同权重、建议包藏在抽屉里基本没人看见（非注意盲视）。**"收益递减"的结论是在缺少进度表征的前提下得出的**；补上仪表盘与步内门禁后向导才成立。设计文档另含对新诊断的逐条原理映射（Hick–Fitts / Sweller 认知负荷 / Kivetz 目标梯度 / Zeigarnik / Reason 错误控制 / 元数据 provenance）。

### 4.3 问题 3 分类查找没发挥 + 覆盖不足（ehentai 借鉴）

| ehentai 机制 | 采纳方式 |
|---|---|
| namespace 强制词表（female:/artist:…） | **已有**（TagKey fixed/open/int 即 namespace）。补「毕业机制」：成为主导航轴的 namespace 毕业为实体（model 本次，task 将来同路），判据即概念文档 §2.4 五问 |
| 上传强制最低标签集 | **采纳（关键）**：网页上传强制 ≥1 model（D6） |
| tag wiki/介绍 | **补课**：fixed 值大量 description 为空，巡检补齐；悬浮提示 / Explore 消费该字段 |
| 同 key OR / 跨 key AND | **修正现有缺口**：当前 `list_demos` 对多个 tag 参数是全 AND——「灰测或 HY4」筛不出来。改为**按 key 分组：键间 AND、键内 OR**（进 B1） |
| 保存的筛选（saved search） | 缓做，Explore 上线后看需求 |
| 个人标签高亮 | 不采纳 |

覆盖不足两步治理：
1. **拆 `type:demo`**：**已落地（2026-08-31，规则版流水线 + 收件箱批准）**。真实语料实测：285 件 `type:demo` 中 201 件可细分（**71%**），批量批准 ≥0.85 的 161 条后 **`type:demo` 44% → 19%**、type 值 **5 → 17 个**、批准 0 失败、重扫幂等 0 新增。详见 `API_CONTRACT.md` §18。
   **顺带查出的两个新问题（原计划没覆盖，待立巡检项）**：① **191 件作品完全没有 `type` 标签**（占已上架 30%）—— 覆盖缺口比 `type:demo` 更底层，规则同样可从 prompt/标题推；② **28 件有多个 `type` 值**（10 件是 `demo`+`game` 这类原有脏数据）—— `type` 语义上应单值，需要一条「多值收敛」巡检 + 合并建议；这两条与 `demo`+新值零重叠已核验（不是流水线造成）。**已进巡检**：`type_missing` / `type_multi` 两项可直接生成候选（实测 191 件里 98 件可由规则补、28 件里 10 件可机械收敛），见 `API_CONTRACT.md` §19。
2. **批次扩 category**（数据可视化/游戏复刻/生成艺术/交互实验…），走「批量建候选 → 审核」流水线，拒绝一次拍脑袋扩 50 个。

### 4.4 问题 4 视图混乱 → 一条规则管所有界面
- **规则**：所有「面板级」标签展示统一青色收起组盒；卡片/列表行内保留 chips（D5，物理空间限制，属"面板 vs 行内"分层而非例外）。
- **实现进度与边界核定（2026-08-31，逐处看过界面后定，见 `API_CONTRACT.md` §23）**：
  - ✅ 探索页描述性标签段改为 `TagGroupBox`（盒头 = 键标签）；标签总览页 / 标签详情页本来就是组盒；
  - ❌ **不转**（核对后判定它们不是"面板级标签展示"，硬转是倒退）：作品卡片行内 chips（D5 明确保留）、详情页 meta 标签区（行内）、作品库筛选条（交互控件不是标签展示）、模型页类型/玩法分布（**数据条**，转组盒会丢数量对比）；
  - 结论：原 §4.4 里"筛选栏 / DemoView 详情标签区"两项列为需改造面，是**当初判错了形态归属**，现按上表核定执行。Q1（卡片行内是否保留 chips）就此确定：**保留**。

### 4.5 问题 5 重要性分层 → `TagKey.tier` 制度化
- `TagKey` 增 `tier INTEGER`：**1 核心**（model，毕业后由 ModelChip 接管位置）/ **2 常用**（type、category、game）/ **3 扩展**（rounds、platform、time、plugin…）。
- 一处元数据驱动全站：上传页顺序与必填性、卡片取哪些 chips、筛选面板排序、Explore 分区。
- 这就是 v2「Tag 退位」的具体形态：TagKey 体系整体降半级为描述层。

### 4.6 Prompt 维度提前（"同 prompt 不同模型"视角）
- 40% demo 已有 prompt，`content_hash` 精确去重 + TF-IDF 相似聚合（纯规则）即可先出**「同提示词的其他模型作品」**模块。
- 与 Task 构成粗细两档：prompt 相近 = 严格复现对比；task 相同 = 同题材对比。
- **Prompt 实体化从阶段 4 提前至 B1~B3**（原计划延后，因用户核心诉求即此视角）。

## 5. 总体概念模型

```
                 MODEL ──────────┐
                   │             │（毕业自 model namespace）
                 TASK ── PROMPT ─│── Run（预留，platform/rounds 为其雏形）
                   │             │
                 DEMO ←──────────┘
                   │
              Rating / Review
```

- Tag 只负责描述；实体负责关系。`tag=model` 双写保留，旧入口不破坏。
- **namespace 毕业机制**（可复用的演进规则）：某 TagKey 成为大众主导航轴（覆盖率 >80% 且点击量集中）→ 毕业为实体；本次 model 毕业，task 直接以实体出生，将来 category 视数据决定。

## 6. 后端设计（性能 / 扩展性 / 可维护性 / 管理接口）

### 6.1 数据模型（DDL）

```sql
-- 模型实体（从 Tag(key=model) 一比一迁移）
models (
  id             INTEGER PK,
  slug           TEXT UNIQUE NOT NULL,      -- /models/{slug}
  name           TEXT UNIQUE NOT NULL,      -- 规范名 "DeepSeek V4 Flash"
  vendor         TEXT,                      -- 沿用 tag.group
  status         TEXT DEFAULT 'candidate',  -- candidate|active|unverified|deprecated
  merged_into_id INTEGER REFERENCES models(id),   -- 废弃不删除
  description    TEXT DEFAULT '',
  created_at DATETIME, updated_at DATETIME
)
model_aliases ( alias TEXT PK, model_id INTEGER FK )  -- "dsv4flash"/"ds-unknown"→canonical

-- 题目实体
tasks (
  id INTEGER PK,
  slug TEXT UNIQUE NOT NULL,
  title TEXT NOT NULL,
  description TEXT DEFAULT '',
  category TEXT,                     -- 对齐 category 标签值，文本起步
  status TEXT DEFAULT 'candidate',   -- candidate|active|merged|hidden
  merged_into_id INTEGER REFERENCES tasks(id),
  created_by INTEGER REFERENCES users(id),
  created_at DATETIME, updated_at DATETIME
)

-- 多对多（D1）
demo_models ( demo_id FK CASCADE, model_id FK CASCADE, PRIMARY KEY(demo_id, model_id) )
demo_tasks  ( demo_id FK CASCADE, task_id  FK CASCADE, PRIMARY KEY(demo_id, task_id) )

-- Prompt 实体（提前，见 §4.6）
prompts (
  id INTEGER PK,
  content_hash TEXT UNIQUE,          -- 规范化后 sha256
  content TEXT,
  created_at DATETIME
)
-- demos.prompt_id FK nullable；demos.prompt 原列保留双写

-- 治理：统一建议收件箱（规则产物；LLM 后置时同表复用，source 区分）
entity_suggestions (
  id INTEGER PK,
  kind TEXT,            -- new_model | new_task | task_match | merge_model | merge_task | alias
  payload TEXT,         -- JSON（建议内容 + 证据摘要）
  confidence REAL,      -- 规则阶段=相似度得分
  source TEXT,          -- rule | user | agent
  status TEXT DEFAULT 'pending',   -- pending|approved|rejected
  demo_id INTEGER NULL,
  created_by INTEGER NULL, reviewed_by INTEGER NULL, created_at DATETIME
)

-- 审计（"任何自动变化可追溯"）
audit_log (
  id INTEGER PK, actor_type TEXT, actor_id INTEGER NULL,
  action TEXT, entity_type TEXT, entity_id INTEGER,
  before TEXT, after TEXT, reason TEXT, created_at DATETIME
)
```

设计取舍：
- **不做冗余计数列**：Model/Task 的 demo 数、平均分全部 `JOIN + GROUP BY` 现算（584 demo / 98 model 毫秒级），避免计数漂移类 bug；阈值 ~5 万条再议。
- **别名表而非物理改写**：归一走 `model_aliases`（O(1) 上传匹配）；真合并 = 单事务迁引用 + `merged_into_id` + 造别名 + 审计。
- 建表走项目惯例 `create_all`；数据迁移用幂等脚本（`--dry-run`，对齐 `recompress_covers.py` 风格），无 Alembic。

### 6.2 服务层

```
services/
  model_service.py    # CRUD/合并/别名/状态机（candidate→active→deprecated）
  task_service.py     # CRUD/合并/挂题摘题/统计
  matching_service.py # 规则层：规范化 + 别名匹配 + TF-IDF 相似召回（纯 Python ~60 行，无 sklearn）
```

`matching_service` 是「LLM 后置」的承重墙，统一签名：
`suggest_task_for(text) -> list[Suggestion]`、`match_model(name) -> Model|None`。
- v2.0 内部：NFKC 规范化 + 去分隔符 + 别名表精确匹配；自实现 TF-IDF 余弦，内存倒排索引，启动惰性构建、变更失效重建（584 篇 <50ms，锁+TTL 模式照抄 `_RELATED_CACHE`）。
- 将来接 LLM：仅改此文件内部实现（召回仍 TF-IDF，重排换 LLM），路由/前端零改动，成本边界焊死在单文件。

### 6.4 性能与迁移
- 索引：`demo_models.model_id`、`demo_tasks.task_id`（复合 PK 不覆盖第二列）、`models.status`、`tasks.status`。
- **顺手修 N+1**：现列表页每条 demo 单发 2 条 COUNT（comment/session_log），20/页=40 查询；serializer 改 `selectinload` 预加载 tag/model/task——v2 字段不加查询数，老页面反而变快。
- 写路径仿 `rating_service.apply_rating_delta` 事务模式：合并/挂题/审核 = 单事务 + 审计行。
- 双写策略：`_set_demo_tags` 同步维护 demo_models / demo_tasks；旧 tag 筛选 URL、agent guide、契约全部兼容。

## 7. 前端设计（专业 / 好用 / 美观 / 高性能）

### 7.1 现状盘点（需求总结）
14 个一级视图 + 30 组件，无 UI 框架，自研 neo-brutalist-playful。**既有语义恰好承接 v2**：
`TagGroupBox` 厂商分组 = Model 分组容器；`mode-badge` = 灰测/未验证徽章；排行榜行 = 对比行母版；`PromptDemoCard` = 提示词卡片雏形。新增需求八项：Model 一等地位、Model 页、Explore 升级、Task 列表/对比详情、同题模块、上传两段式、知识治理 Section、同提示词模块。**零新增依赖**（无图表库/虚拟滚动）。

### 7.2 设计原则 → 具体决策

| 学科原则 | 落地决策 |
|---|---|
| 识别优于回忆（Norman） | 模型全站以 **ModelChip**（厂商色+名称）出现，零手输；上传=可搜索 chips + 申请新模型 |
| 渐进披露 | 卡片四要素封顶（ModelChip/标题/2~3 chips/评分）；task/prompt/会话只在详情页 |
| Hick 定律 | Explore 只露 **Top 12 模型**，其余折叠进厂商分组（复用 GroupedTagValues） |
| 信息气味（信息觅食） | 浏览路径「Demo→Model→同题→另一模型」= 三个实体模块：详情页"同题作品"横滑轨、Model 页"参与题目"chips、Task 页按模型分组行 |
| 小倍数对比（Tufte） | Task 对比 = 每模型一行：缩略图+ModelChip+数量+★均分，按分排序；**不做雷达图/折线**（红线） |
| 双编码/认知负荷 | EntityStamp（首字母方块章，新野兽派原生语汇）+ 厂商色，卡片/Model 页/对比行三处同一视觉身份 |
| 默认与禀赋效应 | 上传 task 步骤="建议+确认+可跳过"，预填不阻断，摩擦 ≤ 现状 |
| 空状态尊严 | unverified 挂灰测徽章照常展示；单 demo task 显示"等更多模型来挑战 →" |
| Fitts 定律 | ModelChip 整体可点 ≥44px；移动端对比行上下堆叠 |

### 7.3 页面规格
- **DemoCard v2**：顶行 ModelChip（≤2 + "+N"），其余不动——瀑布流节奏不变。
- **Demo 详情**：标题下 meta 行加 ModelChip(s) + TaskLink 药丸；页尾「同题作品」+「同提示词」两模块（**两条均已落地**：同提示词 B2′，同题作品 2026-08-31 —— 取 `demo.tasks[0]` 拉题目详情、排除自己、无对照则整块不出现）。⚠️ 现实约束：仿真复验时全站仅 6 件作品挂了题目，所以同题模块当前几乎不显示 —— 这是**数据量**问题不是代码问题，成题量上来（B3′ 候选池 12 exact + 11 similar）才会成为主视觉。MasonryGrid 复用，移动端横滑）。
- **Model 页** `/models/{slug}`：EntityStamp+名称+厂商+状态徽章 → 三格统计（作品/题目/社区分）→ 最近作品瀑布流 → 参与题目 chips。单屏+信息流，无图表。
- **Task 页** `/tasks/{slug}`：题面 → 模型对比行列表 → "用你的模型挑战此题"（`/upload?task=slug` 预填）。
- **Explore**（`/tags` 原地升级，D3）：四段式——模型（Top12+厂商分组）、题目（active task 卡格）、分类、更多维度折叠；右上保留原标签全量入口。
- **管理端「知识治理」**：三栏——概览（覆盖率 KPI 卡）、收件箱（一键通过/驳回，approve 前显示影响面）、实体管理（CRUD + 合并向导**必经 dry-run 预览"将影响 N 个作品"** + 别名行内编辑）。复用 AdminView 壳 + Section 懒加载。
  **已落地（2026-08-31）**，形态从「三栏」改为**六组两级导航 16 面板**（治理总览[体检·审计] / 标签与类型[标签管理·类型细分·巡检] / 知识候选[题目候选·收件箱·归属工作台] / 实体治理[合并向导·别名中心] / 审核与作品 / 社区与站点）——面板数超 5 个后三栏放不下，两级导航是更稳形态；但**原要求逐条落实**：Section 懒加载 ✅、合并必经 dry_run 且预览显示「将影响 N 个作品」✅、收件箱批准前显示影响面 ✅、别名行内增删 ✅。

## 8. 治理与运营

### 8.1 实体状态机
```
Model: candidate ─(admin 确认)→ active ─(合并/退役)→ deprecated
        ds-unknown 类灰测 → unverified（照常展示+灰测徽章，确认后改映射即全量归位）
Task:  candidate ─→ active ─(合并)→ merged / hidden
```

### 8.2 自动化边界（Ai相关.md 四层）
- 能规则不用算法、能算法不用 LLM、LLM 只建议不决定、可自动不扰人。
- v2.0 无 LLM 调用；`entity_suggestions.source` 字段预留 `llm`，接入时仅改 matching_service。

### 8.3 冷启动策略（Task 不会自动长出来 → 先人工点火）
- 手工 seed 5~10 个高热度 Task（我的世界 / 2048 / 蒙娜丽莎 SVG / 物理仿真…）挂现有 demo，**Benchmark 页面第一天就有内容**；
- HWDyzzZ 的 168 个系列上传、HY4×28 / dsv4×28 / glm5.3flash×21 是天然"同题材多模型"坯子；
- 随后规则聚类建议源源进收件箱，人工确认扩题。

### 8.4 KPI（不用"标签数量"当指标）
Tag/Model/Task 覆盖率、candidate 积压数、合并采纳率、建议自动采纳率、Explore→demo 点击路径完成率。

## 13. 不确定型号的三档兜底（Q2 落地补充）

强制 ≥1 model 的前提是**「不确定」有正门**。否则强制只会把人和 agent 逼成瞎编一个型号 —— 那比空着更糟（污染能力数据库的地基）。

### 13.1 四档断言强度（`Model.resolution`，与 `status` 正交）

| 档 | 语义 | 载体 | 后续动作 |
|---|---|---|---|
| `exact` | 精确型号（A） | 正常实体 | — |
| `family` | 知厂商不知型号（B） | `<vendor>-unknown`，`vendor` 有值 | **下钻**：拆到具体型号 |
| `unknown` | 完全不知（C） | 全局 `unspecified` | **归属**：先定厂商再下钻 |
| `guess` | 有猜测未证实（D） | `ds-unknown` / `unknown`，`status=unverified` | **揭晓**：确认后改映射，作品自动归位 |

`status` 管生命周期（candidate/active/deprecated），`resolution` 管「这条断言有多确定」——两轴不混。
**D 必须与 B/C 分开**：把「懒得填」混进 `ds-unknown`，等于毁掉 396 个灰测作品的揭晓资产（仿真已实测到该判定因未规范化而失效，见运维 §14）。

### 13.2 数据与词表

- 兜底位是**真实的 Tag 值 + Model 实体**，不是空值：`model` 是 fixed 键，`_resolve_tag` 只放行词表内值 —— 兜底不进词表，正门就是假的。
- 启动/迁移调用 `model_service.ensure_fallback_models(db)`：建 `unspecified` + 为每个已知厂商（`Model.vendor` ∪ `Tag.group`）建 `<vendor>-unknown`，幂等。
- 登记精确型号时带 `vendor` → 自动补齐该厂商族节点（`get_or_create_model` / `create_model` / `model_update` 三处），保证 B 档永远一键可选。

### 13.3 校验与证据

- `_require_model_tag(s)`：**multipart 创建、from-url 创建、编辑（tags 传入时）** 三处统一强制，且都在下载/解压**之前**（不留孤儿 demo）。
- 错误文案直接写清三条出路（`model:unspecified` / `model:<厂商>-unknown` / 灰测），不让人对着 422 猜。
- 选兜底时前端多问一句 `model_hint`（≤500 字，可选），存 `demos.model_hint`：不确定也要**带着证据不确定**，否则永远不会被收敛。

### 13.4 折叠与归属工作台

- 兜底位**不参与「热门模型」排名**（`list_models(exclude_fallback=True)`），`/explore` 以 `models.fallback_demos` 给出「其他 · 未定 N」折叠计数。
- 显示层：`modelDisplay()` 把 family 渲染成「DeepSeek · 未定型号」、unknown 渲染成「未标注模型」，绝不长得像型号。
- 归属工作台（**已落地**）：兜底实体页 / 管理端「归属工作台」= 待归属清单，批量选中 → 指定真实型号 → 迁回。**必须回写 `model:` 标签**：`update_demo` 会用 `_set_demo_tags → sync_demo_models` 从标签重新派生实体，只改 `demo_models` 的归属会在作者下次编辑时**静默退回兜底位**（回归用例 `test_attribution_survives_later_tag_edit` 专门锁这条）。空操作（`moved=0`）不写审计 —— 变更日志不是操作尝试记录。
- **归属 vs 合并的分工（仿真实测得出）**：规则预填（在 `model_hint` / 提示词 / 标题里找已知型号名）在历史数据上命中仅 **2/82 ≈ 2.4%** —— 因为老数据根本没有 `model_hint`、提示词也少写型号名。所以：
  - **单件判断** → 归属工作台（人看证据，一件件定）
  - **整批揭晓**（如「ds-unknown 其实就是某型号」）→ 走 `merge_model`（一次迁全部引用），不要在工作台里点 396 次
  这条区分是仿真抓出来的：不实测就会把工作台做成一个"看起来能自动、其实要手点到底"的摆设。

### 13.5 URL 约定（slug 必须 ASCII）

- 展示用 `title` / `name`（中文照旧），**URL 用 slug 必须 ASCII**：`slugify()` 剔除非 ASCII，中文题面退化为 `task-N`
- 缘由（仿真抓出）：从中文 prompt 簇「成题」曾生成 `/tasks/仿真题-坦克-科幻-幻坦`，与 Q4「slug 英文化」相反，链接分享时全是百分号编码
- 中文厂商名不得退化成同一个 `vendor-unknown`（会互相改指向）：族节点用确定性哈希后缀 `vendor-<hash6>-unknown`
- ~~后续可给管理端「改 slug」入口~~ **已给（2026-08-31）**：`PUT /admin/models/{id} {slug}`，校验 ASCII 与撞名（撞名 409、非法 422 并回提示可用值），**旧 slug 自动转别名**所以历史标签与外部旧链接仍可解析（详情查找已统一走 id→slug→别名 的单一入口）；审计动作 `slug_set`
- **撤销合并**也已落地（见 `API_CONTRACT.md` §24）：合并审计现在记 `moved_demo_ids`，撤销同样**必须先 dry_run**；早期没有该记录的合并会被如实标为「不可迁回」，只恢复实体、不猜作品归属
