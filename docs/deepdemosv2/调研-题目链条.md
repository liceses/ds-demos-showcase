# 调研：`task → prompt → generation → demo` 链条的现状与设计选择

日期：2026-09-02 ｜ 状态：**调研完成 → 第 6 条（挂题入口）与第 3 条（方案 A 题面块 + 证据表）均已实现**；方案 B（链条小图）列入计划
触发：决策人反馈「题目页面没有提示词啊，没有看到 task → prompt → generation → demo 的链条」。
结论先行：**这不是显示层缺失，是链条本身只有两端有数据**。所以先量清楚，再谈结构。

---

## 1. 数据层实测（真实语料 640 件已上架作品）

| 环节 | 落地形态 | 覆盖率 | 判断 |
|---|---|---|---|
**Model** | `demo_models` 多对多 + 实体表 | **565 / 88%** | ✅ 健康 |
**Prompt** | `prompts` 表（`content_hash` 去重）+ `demos.prompt_id` | **260 / 40%** 有提示词；**239 条独立提示词**；回填率 260/260 | ✅ 机制完好，覆盖率中等 |
**Generation / Run** | **无表**。只有 demos 三列 `gen_rounds / gen_minutes / gen_platform` | rounds **14%** · minutes **9%** · session_logs **0%**（仿真库未搬文件） | ⚠️ 最薄的一环 |
**Task** | `tasks` 表 + `demo_tasks` | **仅 4 道题 / 15 件作品 = 2%** | 🔴 几乎空的 |

补充读数：

- **245 件作品有提示词但没挂任何题**（链条顶端没接上）
- 其中「同一句提示词出现 ≥2 次」的簇只有 **8 个 / 覆盖 17 件** → 可立刻成题的量就这么大
- 收件箱里 `retag_demo` 待批 **139** 条，但 `task_match` 只有 **1** 条 → **没有东西在提议题目**，task 层不会自己长出来
- 提示词长度：p50=96 字、p90=1683、p99=11024、max=18466；**50 件超过 600 字** → 题面块必须折叠 + 展开，不能整段铺
- 36 件作品挂了**多个模型**（链条会分叉，UI 必须能表达"一件作品 ← 多个模型"）
- 现有 4 道题**题面内部提示词完全一致**（4/4）→ 目前"题面"能代表整题，但这会随规模破掉（见 §4）

## 2. 文档原意核对（避免我凭空发明结构）

- `v2理想设想.md` §76 定义链条 `Task → Prompt → Run → Demo`；§81-87 画的正是「Run #1 ❌ → Run #2 ⚠️ → Run #3 ✅ Demo」的多轮过程记录。
- **但 `Run` 是刻意不建表的**：`ds的建议.md` idea 3 原话「Run 别建表，但 rounds/time/platform 现在就该收编成 Run 元数据 —— 没有数据来源的表就是死表」。已按此落地为 B5′ 三列（`落地计划.md` §117：`Run（预留，platform/rounds 为其雏形）`）。
- 同时文档写明「Prompt / Run 先保持现有系统兼容，以后再补」。

**所以现状是"按计划的样子"，不是遗漏。** 但计划里没预料到的是：**task 层实际长不出来**（2%），于是链条视图会是一具空骨架。

### 一个结构性事实（决定一切）

`demos.prompt_id` 是**单值外键** → 一件作品只能有一个提示词。
所以理想设想里"同一件作品经历多次 Run、每次不同 Prompt"的图景**当前无法表达**，除非：
(a) 建 `runs` 表（demo 1—N run，run 带 prompt/轮数/耗时/结果状态）；或
(b) 承认"一次上传 = 一次生成"，把多轮过程放进 `session_logs`（已有表，只是仿真库没文件）。

## 3. 为什么"看不到链条"：三个独立缺口

| 缺口 | 位置 | 性质 |
|---|---|---|
① 题目页**完全没有提示词展示位** | `TaskDetailView` 只有 标题/分类/计数/描述 + 对比行 + 作品瀑布 | 显示缺失（可立即修） |
② "generation" 环节在 UI 上只有两个数字（ROUND/MIN），且 86%/91% 是空 | 对比行里 | 数据缺失 + 显示弱 |
③ task 归属只有 2%，链条顶端无内容 | 数据 | **流程缺失**（见 §5） |

只修 ① 会得到"题面 + 4 道题 + 15 件作品"的漂亮空壳。**必须三件一起考虑。**

---

## 4. 一个调研中发现的真问题（比 UI 更重要）

**"同题对比"的有效性前提没人检查**：如果挂在同一道题下的作品其实用的是**不同提示词**，那它就不是 benchmark，只是"主题相近的作品列表"。

现在 4/4 道题恰好一致，所以没暴露。一旦靠 `task_match`（语义相似）批量挂题，就会出现"题面不同却同题对比"的假比较。

→ **UI 应该把"题面是否同一句"作为一列显示出来**（信息科学：把结论成立的前提条件显式化，而不是让用户猜）。
→ 治理上需要一个规则：挂题时提示词不一致的，要么标注"非严格同题"，要么要求管理员确认。

## 5. 设计方案（三个，含推荐）

### 方案 A：题面块 + 证据表（**推荐**）

```
┌ 题面块 ─────────────────────────────────────┐
│ [题面] 做一个复杂的硬表面结构的3d科幻坦克…  │  ← description 优先，否则统一提示词摘录
│ 来源：4 件作品使用同一句提示词 ✓ 严格同题   │  ← 把有效性前提说出来
│ [折叠：全文 18466 字 ▾]                     │
└─────────────────────────────────────────────┘
按模型对比（保留现有 Benchmark 行）
┌ 证据表（一行一件作品，链条从左到右）────────┐
│ 模型        题面      生成过程      作品      评分 │
│ dsv4-flash  同一句 ✓  3轮 · 12分    → 作品名  ★4.8(23) │
│ grok-4      不同 ✗    — · —         → 作品名  ★4.2(3)  │  ← 缺数据就显示 —，不填 0
│ HY4         同一句 ✓  7轮 · —       → 作品名  ★4.6(11) │
└─────────────────────────────────────────────┘
```

- 证据表**取代**现在的"全部作品"瀑布（瀑布把链条信息全丢了，且同样有 24 件截断问题）
- 列 = 链条的环节，读表 = 读链条；可排序（评分/轮数/耗时）、可筛（题面一致/不一致）
- 空环节显示 `—`（现有 `task_compare` 已经是"AVG 忽略未填返回 null，不用 0 冒充数据"的规矩，延续它）
- 符合本站"科研记录"的品牌语汇（表格、编号、出处），不像仪表盘玩具

### 方案 B：链条图（DAG 可视化）

好看，但：4 道题 15 件作品时是玩具；SVG 图对读数字、比较、搜索都更弱；键盘/屏幕阅读器不可达；移动端不可用。
→ **不建议做主形态**。若要做，只在**单件作品页**做"我这一条链"的小图示（模型 ← 题面 ← 作品），作为辅助理解。

### 方案 C：只补题面块（最小改动）

在题目页 hero 下加一块题面（description 或统一提示词，长文折叠）。
→ 1 小时能做完，但**不解决"看不到链条"**，只是补了 §3 的缺口 ①。

**推荐：A（内含 C 的题面块）**，并把 §4 的"题面一致性"作为表里的一列。

## 6. 但 A 做完仍然只有 4 道题可看 —— 必须同时处理数据增长

链条要可见，先得有内容。三条现实路径：

| 路径 | 现状 | 代价 |
|---|---|---|
**P1 把 8 个可成题簇立即成题** | 后台「题目候选」已有此能力（预览→执行），只是没批量做 | 零开发，管理员操作 10 分钟；题目数 4 → ~12 |
**P2 让 `task_match` 提议跑起来** | **查清了，不是 bug，是没接线**：`_queue_task_match()` 只在 `challenge_task` 存在时被调用（用户从题目页点「挑战此题」带 `?task=` 进来）；而 `task_service.suggest_for_demo()` 目前**只被一个搜索接口使用**（`GET /tasks/suggest?q=`，为"输入时提示相似题目"设计） | 无需排查 —— 缺的就是 P3 那个入口
**P3 上传页提供"选题目"入口** | **完全没有**（决策人第 6 条正是这个）：现在只能从题目页点"挑战此题"带 `?task=` 进来，上传页里无法主动选题挂题 | 前端为主 —— 后端 `/tasks/suggest` 与 `_queue_task_match` 都已就位

### 结论（比初稿更强，并修正一处猜测）

初稿这里写的是"可能是 bug，需排查"。查证后：**提议引擎（`suggest_for_demo`）、候选队列（`_queue_task_match`）、
查询接口（`/tasks/suggest`）三样都在，唯独没有任何 UI 在上传时调用它们**。
`/tasks/suggest` 现在处于"建好了没人调用"的状态 —— 它存在的唯一理由就是上传页的那个题目选择器。

所以**第 6 条（上传页挂题入口）应排在第 3 条（链条可视化）之前做**：先让作品能挂上题，
链条视图才有内容可显示；否则做出来是 4 道题的空骨架。作者手里有作品、有提示词，
但没有任何地方能让他说"我这件是答某道题的" —— P1/P2 都只是管理员侧推着走，推不动 2% 这个数。

## 7. 需要你拍板的事

1. **方案选 A 还是 C**？（我推荐 A；B 只在作品页做辅助小图）
2. **`Run` 到底建不建表**？
   - 不建（维持文档原意）：generation 环节永远只有"轮数/耗时"两个可选数字；
   - 建：能表达"多次尝试 → 最终作品"，但**需要数据来源**（agent 上传时愿意填吗？session_logs 里有吗？）—— 我倾向先查 `session_logs` 真实内容再决定，不要为了画图好看造死表。
3. **"题面一致性"作为一列**是否同意？进一步：**是否要立规矩**——题面不同的作品挂同一题时，必须在页面上标"非严格同题"？
4. **P3（上传页选题挂题入口）是否现在做**？它和你的第 6 条反馈是同一件事，我认为优先级高于链条可视化。
5. 证据表是否**取代**题目页现在的作品瀑布？（我推荐取代：瀑布丢信息且有 24 件截断）

## 8. 我明确不做的

- 不做 DAG 大图作为主形态（理由见方案 B）
- 不为"generation"环节编造数据或用 0 填充（延续 `task_compare` 的 null 规矩）
- 不在链条视图里放综合评分/雷达图（文档红线：不给综合结论）
- 不为了题目数量好看而放宽成题门槛（阈值 0.35 是线上语料标定过的）
