# 内存持续增长审查：deepdemos.top 后端（2026-09-01）

- 审查对象：**当前部署代码 = HEAD `6874fa5`**（含 2026-09 连接池紧急修复；工作区另有未提交的 v2 代码，未部署，本报告不覆盖）
- 部署形态：单 worker（`uvicorn --workers 1`）→ 所有模块级全局变量都在同一个进程里累积，只进不出的全局状态永远不会被换进程清零
- 审查方法：枚举 `backend/app` 全部模块级可变全局（`dict/list/set/deque/defaultdict`）、全部 `Thread` 生成点、全部缓存装饰器，逐一核对 key 来源与淘汰逻辑

## 结论

**存在真实的内存泄漏，属于同一类模式：按外部输入（IP / slug）为 key 的全局字典，只清理时间戳、从不删除 key。** 单条目约 0.2~1KB，爬虫与漏洞扫描器带来海量唯一 IP / 随机 slug，日积月累表现为 RSS 缓慢爬升。另有若干「有界但偏大」的缓存值得知晓。连接池、线程、会话等经典泄漏点已逐一排除。

## P1 · 确认泄漏：限流字典按 IP 只进不出（8 处）

统一模式（以 `stats.py` 为例）：

```python
_visit_hits: dict[str, list[float]] = defaultdict(list)
...
_visit_hits[ip] = [t for t in _visit_hits[ip] if t > now - 60]  # 只剪当前 key 的时间戳
_visit_hits[ip].append(now)
# 没有任何地方 del _visit_hooks[ip] / pop / 定期清扫 → key 永生
```

| 位置 | key | 流量来源 | 增长速度 |
|---|---|---|---|
| `routers/sessions.py:20` `_hits` | ip | **GET** /demos/{slug}/session-logs，爬虫可直接刷 | 快 |
| `routers/tags.py:38` `_suggest_hits` | ip | GET 标签建议，爬虫可刷 | 快 |
| `routers/stats.py:19` `_visit_hits` | ip | POST /stats/visit，前端打点（真实访客 IP） | 慢 |
| `routers/stats.py:48` `_heartbeat_hits` | ip | POST /stats/heartbeat，30s 一次（真实访客 IP） | 慢 |
| `routers/forum.py:35` `_hits` | bucket(ip) | 发帖限流 | 慢 |
| `routers/ratings.py:24` `_anon_global_hits` | ip | POST 评分；扫描器也会乱 POST | 中 |
| `routers/ratings.py:23` `_anon_demo_hits` | **(ip, slug) 元组** | 唯一 IP × 唯一 slug 笛卡尔积，增长最快 | 快 |
| `routers/demos.py:42` `_anon_uploads` | ip | POST 匿名上传 | 慢 |

估算：每唯一 IP 每字典约 0.3~0.5KB（dict 槽位 + IP 字符串 + 时间戳 list）。扫描器一天几千个唯一 IP 就是每天几 MB；`_anon_demo_hits` 的 (ip, slug) 组合键放大得更快。**增长主体是爬虫/扫描器流量，不是真实用户。**

## P1 · 确认泄漏：scope.py 预览门禁的两张「永生」表

`services/scope.py:75`、`:78`：

- `_vis_cache: dict[slug -> (过期时刻, sites, status)]`——TTL 判定只在**读取时**跳过过期值，过期条目和垃圾条目永远留在 dict 里；
- `_slug_locks: dict[slug -> threading.Lock]`——single-flight 修复（连接池事故）引入，**为任何请求过的 slug 建锁，包括不存在的**，锁对象永不回收。

暴露面：`demo_public_in_scope()` 在**每个** `/preview/{slug}/...` 子资源请求上执行，slug 完全由 URL 提供。爬虫扫 `/preview/随机串/v1/xxx` 就能源源不断制造永久条目（每个 ~0.2-0.3KB，锁对象更重）。

## 已排除的嫌疑（逐一核对过）

- 无 `lru_cache` / `functools.cache`（HEAD 全库 0 处）；
- 线程只有 2 个常驻 daemon（visits 落盘 flusher、oss-sync 按需单例），无每请求建线程；
- SQLAlchemy：请求会话 `get_db` finally close；后台会话（visits/site_info/scope/notification）全部 try/finally close；连接池上界 40；
- 上传路径 PIL 用 `Image.open(io.BytesIO(...))`，无文件句柄泄漏；zip/下载均带上下文管理器与大小上限；
- 中间件仅两层 `@app.middleware("http")`，现代 starlette（fastapi>=0.115 对应 >=0.37）无已知 BaseHTTPMiddleware 泄漏——但 requirements 全是 `>=` 无锁文件，容器内实际版本不可考，见建议 5。

## 建议修复

1. **统一限流器**（治本，改动集中）：新建 `services/rate_limit.py`，提供一个带定期清扫的限流器（后台线程每 5~10 分钟丢掉「最新时间戳已出窗」的 key；或每次调用时若 `len(dict) > 阈值` 就全表扫一遍过期 key）。7 个路由全部换成它，顺带消灭 8 份重复代码。
2. **scope 两张表定期对账**：清扫定时器里同时处理——删 `_vis_cache` 中过期条目，删 `_slug_locks` 中「不在 `_vis_cache` 里」的锁（正在 single-flight 等待的线程极少数，清扫间隔足够长即安全）。
3. **`_RELATED_CACHE` 顺手加同样的过期清扫**。
4. **（可选）把明显的扫描器流量挡在 Cloudflare**：session-logs、tags suggest 等爬虫可刷的 GET 端点配 CF 限流规则，既防内存增长也省源站。
5. **验证手段**（先量化再修也行）：
   - `docker stats` / cgroup RSS 拉 24-48h 看斜率；真泄漏是持续线性，glibc/pymalloc 高水位是「冲高后平台期」；
   - 所有嫌疑字典都是模块级全局，加一个 admin 专属 debug 接口（或每 10 分钟打一行日志）输出各 `len()`，与 unique IP 数对账即可定罪；
   - 需要精确定位再上 `tracemalloc` 快照差分或 memray。
6. **部署 v2 前复查**：工作区未提交的 v2 服务（cluster/matching/task 等）不在本次审查范围，上线前按同样清单过一遍模块级全局状态。
