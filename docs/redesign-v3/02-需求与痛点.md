## 0. 一页结论（TL;DR）

1. **需求已演进出三层**：L1 原始 13 条（idea.md）→ L2 运营期长出的社区/论坛/通知/声望/模型库（README 未记账）→ L3 v2 战略「从作品库到模型能力数据库」。**文档负债先于代码负债**：README 的需求↔实现表仍停留在 L1，L2 的 6 个新页面完全无文档。
2. **v2 的核心结构性痛点不是代码，是「数据长不出来」**：Task 覆盖 2%、Run 元数据 9~14%、同题对比的有效性前提（题面一致性）无人保证。链条 `Task→Prompt→Run→Demo` 两端有数据、中间空转。
3. **「有引擎没方向盘」是最大的增量痛点族**：用户排行榜、粉丝/关注列表、排行榜时间窗、公告↔论坛互链（创建侧）等后端已就绪的能力，前端 0 入口——这是 v3 最便宜的需求池。
4. **注册用户的价值闭环是断的**：无找回密码、无 OAuth、注册收益仅「能评论/发帖」，而匿名者也能上传——注册动机弱 → 488 用户 vs 63% 作品署名 public/灰测。
5. **增长路径上最先崩的是治理侧不是展示侧**：列表页 SQL 已优化到恒定 8 条，但收件箱 140+ 待批、归属工作台 374 件、人工判断 2.4% 命中率的预填——**Demo 增长 10 倍 = 管理员工作量增长 10 倍**，与 v2 制度目标（「Demo 增长 10 倍，人工只增 2~3 倍」）背道而驰。

### 1.3 L3 · v2 战略需求（作品库 → 模型能力数据库）

定位宣言（v2理想设想）：**不收集作品，积累数据**——`Task → Prompt → Run → Demo` 链条 + 横向比较 = 「可体验、可追溯、可比较」的能力观察，区别于普通 Benchmark 的「一个分数」。

六实体：Model（谁做）/ Task（做什么）/ Prompt（怎么要求）/ Run（怎么生成）/ Demo（做出什么）/ Rating（怎么看）。**Run 刻意不建表**（评审 R 系列裁决：无数据来源的表是死表，收编为 `gen_rounds/gen_minutes/gen_platform` 三列）。

四层自动化铁律（Ai相关.md）：**规则 → 算法 → LLM → 人工**；LLM 只建议不决定（`entity_suggestions` 收件箱 + confidence 三级阈值 0.99/0.60）；v2.0 零 LLM 调用，`matching_service` 单文件是「LLM 后置承重墙」。

治理制度：创建/维护分离、废弃不删除、一切变更可追溯（audit_log）、合并必经 dry_run、候选不外泄、写操作全走 service。目标姿态：**「Demo 增长 10 倍，人工工作量只增加 2~3 倍」**（v2理想设想 §11.3）。

## 3. 痛点提炼【交付②】

### 3.1 结构性痛点（v2 文档裁决汇总——v3 必须继承的背景）

| # | 痛点 | 证据（v2 实测） | 来源 |
|---|---|---|---|
| P1 | **Task 层长不出来：链条顶端空转** | Task 仅 4 道/15 件 = 2%；`suggest_for_demo`/`_queue_task_match`/`/tasks/suggest` 三件套齐全却只有上传页一个调用口；管理员侧「成题」推不动（245 件有提示词无挂题，可立即成题簇只有 8 个/17 件） | 调研-题目链条 |

### 3.2 增量痛点（本文独立审码新发现）【交付③】

**A. 有引擎没方向盘（§2.2 全表）**——最便宜的需求池：用户排行榜 / 粉丝关注列表 / 榜单时间窗 / 公告互链创建侧 / 标签介绍悬浮消费。

**B. 账号体系是单点断链**〔增量〕：
- 无找回密码：仅有登录态下的 `change-password`（auth.py 全文实查）——**忘密码 = 账号永久失联**，其名下作品（作者 tag）无人能认领；
- 无 OAuth（gh 登录 idea todo 至今 ❌）、无邮箱绑定——注册收益只剩「能评论/发帖/被通知」；
- 而上传（站点核心动作）**匿名即可** → 注册动机被结构性削弱，也解释了 488 注册用户 vs 头部贡献者集中（HWDyzzZ 168 件）与 public 65 件的格局。
- **v3 判断**：这是需求而非工程问题——要么给注册一个「非它不可」的价值（如认领 public 作品、follow 流、通知闭环），要么接受「轻注册」定位并把找回通道（哪怕邮箱外置）补上。

**C. 匿名聚合页是死胡同**〔增量〕：`/author/public` 固定 `page_size: 50` 无分页无筛选（PublicView 实查）——public 名下 65+ 件（且持续增长）超过 50 件即**静默截断**；也无 agent/人工区分（v2 的 Known/Unknown 分离思想未延伸到作者维度）。

**D. 预览 iframe 无加载/错误态**〔增量〕：DemoView 的 web 预览 iframe 懒挂载后，**无 `@load`/onerror 处理**——加载中只有空白、加载失败（CORS/被墙/大文件慢）无提示（决策人 12 条反馈中「预览加载/错误的鲸鱼动画」仍未做，`dv-standin` 卡只覆盖 zip/link 类型）。iframe 是本站第一交互面，这是体验层最裸露的缺口。

**E. 搜索是 LIKE，无相关性**〔增量〕：`list_demos` 搜索 = `title/description/tag-concat ilike %q%`（demos.py:387-391 实查）——无分词、无拼音/错别字容忍、无相关度排序（中文标题命中率靠运气）；治理文档 §45「Search Index 与数据库分开考虑」已预告此债。规模小可容忍，**语料 5k+ 后「搜不到」会从体验问题变成信任问题**。

**F. 上传页是 1299 行 / 70KB 的单体组件**〔增量〕：v2 重设计把四步向导、仪表盘、建议包、草稿、挑战、编辑、可玩性全部塞进一个文件——功能正确但**可维护性已成负债**（任何改动都在高风险区动刀；v2 文档自己也记录了多次编辑事故）。v3 重设计若再加重上传页，应先做组件拆分（步骤条/仪表盘/建议包/草稿均是天然边界）。

**G. 后台用户管理无分页**〔增量〕：AdminUsersSection 是唯一没有 PaginationBar 的管理面板（组件目录 grep 实查，AdminDemos/Forum/Audit 均有）——488 用户 × 增长后「第 100 个用户」不可达。此为决策人 12 条反馈中明确点名「后台用户管理分页」的**未兑现项**。

**H. 管理端实体选择器 200 上限**〔增量〕：AdminAliasesSection 拉取 `page_size: 200` 硬编码——模型实体破 200 后（现 116+，迁移口径 101），别名中心的下拉**静默截断**，管理员将选不到排在后面的实体（EntityPicker 有搜索没事，别名中心没有）。

**I. 模型删除/退役没有正面入口的语义缺口**〔增量〕：合并向导覆盖「A 并入 B」，但「这个实体本来就是错的/垃圾」只有 status 置 deprecated（裸状态机接口），无 UI 引导、无「退役后作品去哪」的说明——对照 v2 治理文档「废弃而不是删除 + 展示层过滤」，链条存在但管理员心智路径缺失（小痛点，列出不展开）。

**J. 通知只覆盖「被动事件」，缺「关注驱动」**〔增量〕：通知 5 类型全是审核/回复/赞——**关注的人上传了新作品 / 关注的题目来了新作业（挑战）没有通知**。关注体系有数据（follow 表）无反馈回路，「关注」对用户无持续价值 → 反哺 B（注册动机弱）。challenge_task 落地后「题目有新提交」是天然通知源，后端通知服务已就绪，只差触发点。

**K. 排行榜语义与 v2 红线的关系未决**〔增量〕：神鬼榜（作品级）与模型社区分（收缩分）两套口碑并存，但「排行榜」导航位只有作品榜——用户「看哪个模型最强」的唯一入口藏在 /models 排序里。v2 红线明确「不做综合排名结论」，但**入口组织**上「模型口碑」没有一级页面（/models 的 score 排序实质就是模型榜）。v3 需要一个明确决断：模型口碑榜是否升为一级入口（仍以 score+样本档呈现，不下结论）。

**L. i18n 只覆盖壳层**〔增量〕：约定「只翻 UI 固定文案，UGC/标签值/管理后台不翻」——管理后台 18 面板全中文，英文管理员不可用；标签值（中文 game 值等）在英文站原样。当前可接受，但「海外橱窗 astra 全英文 + 主站中英混合」的品牌一致性是 v3 决策点。

**M. 移动端预览体验天花板**〔增量〕：Demo 页窄屏已做布局适配（标题 718px→150px 等），但 iframe 预览在手机上仍是「能看不能玩」（高度受限、无横屏引导、无「在外部浏览器打开」快捷通道）。对「可体验的真实结果」这一定位，移动端是流量大头时的第一伤害面。

| **收件箱/归属** | **140+374 待办**（P5） | 人工消化追不上上传速度 | **必须提高自动采纳率**（LLM 后置承重墙到期：confidence≥0.99 自动执行目前 v2.0 关闭） | 无 LLM 不可运营 |
| **管理后台** | 18 面板侧栏+徽章 ✅ | 面板继续长（预计 >22）——侧栏分组需对象×动作重排（IA 已设计待三期） | 深链+批量操作成为刚需（P9） | 多管理员/角色分权（治理文档 §27 四角色） |
| **论坛/通知** | 轮询 30s 心跳+未读轮询，可接受 | 轮询风暴初现（用户数↑） | **应改 SSE/长连接** | 通知分优先级+邮件外发 |
| **上传体验** | 四步向导成熟 | 建议包采纳率待观测（数据无采集） | 词表抽屉必须重做（上） | agent 上传占比高 → 结构化元数据直填（绕过向导）优先 |
| **评分/口碑** | 收缩分+样本档 ✅ | 作品级样本档需求（4.1） | 防刷凭证（device_id 不够） | 时间衰减/近 90 分副指标（v2 明确不做，届时重议） |
| **账号体系** | 单点断链（B） | 找回密码成客服黑洞 | OAuth 必要 | 认领 public 作品机制 |
| **会话日志** | 限流 60/h ✅ | 存储成本（OSS 备份已备） | 检索需求（跨作品搜会话内容） | 过程数据成产品（Run 实体到期重议） |
| **astra/多视区** | 白名单制 ✅ | 新增子路由默认 404 ✅（机制健全） | 多视区配置化 | 无压力 |

**核心结论**：展示侧（列表/瀑布/分页）被 v2 打磨得很耐操，**1k 量级前没有性能悬崖**；真正的悬崖按先后顺序是——①治理侧人工消化能力（现在已到临界，140+374 待办）→ ②搜索质量（3k）→ ③SQLite 写并发（1w）→ ④无 LLM 不可运营（贯穿）。**v3 的投入应压在「治理自动化 + 数据质量入口」而非展示层翻新。**

## 6. 需求判断：v3 该做什么、不该做什么

### 6.1 红线（继承 v2 全部裁决，v3 不得推翻）

不做模型能力雷达/Token 成本曲线/SOTA 综合排名/复杂折线；不给综合评分结论；LLM 只建议不决定；候选不外泄；合并必经 dry_run + 审计；slug 必须 ASCII；契约只增不改（golden 快照护栏）；新一级对象不占顶栏导航位（从探索下钻）；「假动作比没动作更坏」（无自动补救能力不给按钮）；验证 = 重启后看图 + CDP 断言 + 真实语料仿真。

### 6.2 v3 需求方向（按「痛点 × 价值 ÷ 成本」排序）

1. **把「有引擎没方向盘」的五件事接上**（§2.2 A1~A5）：用户声望榜 Tab、粉丝/关注名单页、榜单时间窗、公告互链输入、标签介绍悬浮消费——全部是纯前端 + 既有接口，合计 ≈3 天，直接补齐 README 未记账的 L2 功能面。
2. **出题的用户侧通道**（P1 的根治而非续命）：「游客/作者出题」走与挑战同构的候选制（`task_proposal` 建议 kind），上传页与题目页给「没有这道题？出一题」出口——把 Task 增长从「管理员侧推」变成「作者侧拉」。这是对 P1 的最小制度补丁，不违反「禁止无审查自动创建 Task」（治理文档背书）。
3. **预告机制（P4 的业务化）**：灰测池/兜底池的「揭晓待办」做成概览台常驻卡（池龄、件数、最近一次揭晓时间）——把「某天主动发现」变成「系统定期逼问」。
4. **收件箱批量消化**（P5）：retag 类候选批量批准（已有先例 161 条 0 失败）+ 按 kind 分节的批量 UI；同时采集「建议采纳率/驳回理由」作为 LLM 接入前的基线数据。
5. **注册价值闭环**（B/J/C）：找回密码通道（邮箱或站点外约定）+ public 作品认领机制 + 「关注的人/题有更新」通知触发点——三者是一件事（让身份有持续价值）。
6. **预览加载/错误态**（D）：决策人已点名，半天的活，体验收益/成本比全站最高。
7. **搜索质量路标**（E）：v3 至少给出 FTS5（SQLite 自带）的迁移预研结论，不急于实施。
8. **上传页拆分**（F）：跟随功能迭代顺带做，不单独立项。

### 6.3 非目标（v3 明确不做）

- 不做 Explore 四段聚合大页（D3 裁决：模型+题目两入口已够，第三个聚合页是重复）；
- 不建 runs 表（无数据来源，R 系列裁决维持；「多次重试」过程记录归 session_logs 叙事）；
- 不做链路 DAG 大图（调研方案 B 否决维持）；
- 不做模型「综合能力」页与跨题排名（红线）；
- 不做批量自动挂题/自动改标签（R10/R11 裁决维持：三段式与人工批准）；
- 不翻 UGC/管理后台（i18n 边界维持，除非 §6.2-5 做了英文运营定位变更）。
