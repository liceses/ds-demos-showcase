# 06 · 后台实体统一管理与顶栏重设计方案（双方案）

> **输入**：用户点名痛点两条——A「没有对模型，题目，等实体的统一管理，不能自由设置」；B「顶栏还是不好看，重新设计」。
> **性质**：先方案不动手，**零代码**。基线 main=bac4363（M2 四批已并入）。
> **引用源**：02-需求与痛点 §1.3/§3.1/§4.5/§6.1；v2理想设想 §七（治理体系）；03 §2.4（topnav 定稿）/§9.3（工作台待办驱动）；05 §1（stylekit 语汇）/§5（三律）。
> **写作立场**（captain 追加）：A 线的灵魂=「自由设置」与治理制度的平衡——自由设置是**在治理语义内做足**，不是无治理的自由 CRUD，也不拿红线当不做功能的借口；B 线静默化两轮未让用户满意=方向可能错了，这次**加设计而不是再减法**。

## 0. 一页结论

- **A 线**：用户说的「不能自由设置」拆开是四个具体缺失——**没有单一实体入口**（找一个 Model 要跨合并向导/别名中心/归属工作台/词表四处）、**无字段直改**（改一句 description 只能走候选或 SQL）、**状态不可见不可操作**（candidate/active/deprecated 生命周期散在代码语义里，UI 无处安放）、**关系无总览**（alias_of/merged_into 散在四个面板）。方案=在 admin 内立**知识中心域**（Knowledge Center 落地第一步）：统一实体总表 + 统一实体详情模板（概要/关系/生命周期/审计/关联作品五区）+ 实体 CRUD 矩阵（字段级裁决哪些自由编辑、哪些走候选、哪些只读）。P3 最小集=侧栏归组+实体总表 v1+实体详情 v0，**纯前端可落地**；字段直改与状态跃迁端点列入后端协作清单，P4 接。
- **B 线**：顶栏的病根不是「还多了什么」，而是两轮手术后**丢了形态记忆点**：一轮静默化把导航去形态化（边框盒+荧光章被剥成文字），二轮减法治理了数量（6→4）却没治理**节律**（四条 13px 大写灰链+五枚边框小钮+CTA 同灰度一排到底，无字重层级、无分段、无唯一记忆点）。方案一「报头 MASTHEAD」（推荐）：不碰 6→4、不动 tokens，用**字形升档（13→15px/800、字距 0.05em）+ 激活态双层下划线章 + 三段竖分隔线 + 80/64 双档高度 + 吸顶硬切缩矮**五个「加法」把报头气场做回来；stylekit 的五条硬参数全部转译进 4 枚 header 专属 token，R7（0ms 硬切）/R8（零倾斜）全兼容。

# 第一部分 · 任务 A：知识中心——后台实体统一管理方案

## A1. 问题定义：把用户原话翻译成治理语义

用户原话：「没有对模型，题目，等实体的统一管理，不能自由设置」。

逐词解剖（对照 02 §4.5 管理员步进表）：

| 用户语义 | 现状实查 | 差距本质 |
|---|---|---|
| 「没有统一管理」 | Model 的管理动作分散四处：合并→合并向导、别名→别名中心、归属→归属工作台、词表字段→标签词表（仅 Tag）；**没有任何一页能「以实体为中心」纵览** | 缺「实体为中心」的视图（现在的面板全部以「动作/队列」为中心） |
| 「不能自由设置」 | 改 Model.description：无 UI（候选流只覆盖 kind 固定的建议）；改 Tag 介绍：巡检只能批量补、无单件直改；Task 题面：批准后不可再编辑；状态：unverified/active/deprecated 存在于数据但**无一处可操作** | 缺「管理员直改」通道——自由编辑被误解为「只能走候选」，实际 v2 制度从未禁止**管理员直改**（管理员=边界判断者，正是「人工做边界判断」的那个人） |
| 「对模型，题目，等实体」 | 六实体中 Model/Task/Tag/Alias 有管理面，Relation（alias_of/merged_into/parent_of/related_to/implies）只作为合并/别名的副产品存在，无独立读口 | Relation 是 v2 §7.5 的核心抽象，前端零承载 |

**「自由设置」的正确定义**（本方案的灵魂）：
> 自由 = 管理员对实体**形态字段**（名称/描述/分组/关系）拥有直改权——代价是每笔落审计、全部走 service、可追溯可回滚；
> 制度 = 对实体**身份与存在**（canonical 归属、合并、删除、批量外溢）保留审批/预览/废弃制。
> 一句话：**改「内容」自由，动「身份」有闸。** 修改 Model 的描述是内容；把 dsv4flash 并进 dsv4-flash 是身份。

## A2. 治理语义内的实体 CRUD 矩阵

红线对照（全部继承，一条不破）：LLM 只建议不决定（§7.6 安全边界）；候选不外泄（低置信默认不进视图）；合并必经 dry_run+影响面+可撤销；**废弃不删除**（无物理删除按钮，全站）；变更全审计（谁/何时/改什么/前后值/理由）；写操作全走 service；「假动作比没动作更坏」（R11——无后端能力的按钮不给）。

### A2.2 字段级细化（Model 样板——其余实体同构给出）

| 字段 | 现状 | 裁决 | 说明 |
|---|---|---|---|
| display_name | 无直改口 | **自由** | 规范化大小写/空格=§7.6「AI 可自动做」清单的同款人工权 |
| description | 无 UI | **自由** | 多行文本+保存即审计 |
| vendor | 归属工作台间接改 | **自由** | 下拉选既有厂商或新建（新建厂商=candidate） |

| created_at / created_by | 派生 | **只读** | 审计权威 |

**给「自由」的护栏注记**：自由编辑三律——①保存即审计（before/after/理由）；②写操作全走 service（Admin UI 与 AI Worker 同规则，§7.8）；③危险度分级（自由=普通审计行；受限=dry_run/预览/二次确认）。管理员直改**不产生候选**——候选流是给「非管理员贡献者」的，管理员的直改权就是治理制度里「人工做边界判断」的执行面。

### A3.3 生命周期状态机 UI（对齐 v2 §7.3，按现库语义收窄）

现库实况：Model 已有 active/unverified（+guess 兜底档）、deprecated 字段存在但无 UI；Task 无状态机（R3 押后项到期）；Tag 只有 active/hidden 二态。状态机按「现库语义 + v2 §7.3 目标态」收窄设计，**不发明现库不存在也暂不需要的状态**：

# 第二部分 · 任务 B：顶栏重设计 v2

## B1. 病理反思：两轮为什么不满意

- **一轮（M1-H1 静默化）**：把 05 §1.3-M1「静默导航」整体移植——nav-link 从边框盒改纯文字链。问题：stylekit 的静默导航成立靠**色阶系统**（muted/foreground 两级灰阶+200ms 色过渡），本站抄了「去框」却没抄色阶层次，且 R7 裁决换色 0ms 硬切——结果=导航失去一切状态质感，野兽派辨识度（边框/章）一起被剥掉。**去形态化过度**。
- **二轮（M1-fix-10b）**：6→4 减法正确且不推翻（本次约束确认）。但减法只管了「数量」，没管「排布节律」：四条 13px 大写灰链 + 五枚边框小钮 + 一枚红 CTA，**同灰度、同字号、同基线一排到底**——像表格工具条，不像报头。「好看」缺的是**层级、节律、唯一记忆点**，不是更少的元素。
- 推论：这次要「加设计」——加字形层级、加节律分隔、加唯一彩色记忆点；而不是把上一轮删掉的东西原样加回来（退回按钮化 nav=推翻静默化裁决，同样不干）。
