# 内存水位复盘：862MiB 的 glibc arena 虚胖（2026-09-02）

> 起因：容器重启后 `01:00 <50% → 06:00 60% → 14:00 70%`，怀疑内存泄漏。
> 结论：**不是对象泄漏，是 glibc 多线程 arena 各自攥住已 free 的内存不还 OS**（"虚胖"）。
> 修复：`docker-compose.yml` 加 `MALLOC_ARENA_MAX=2` 等（见 §5）。相关代码修复见 commit `6874fa5`。
> 环境：雨云 HK，2GB 内存，**无 swap**，`uvicorn --workers 1`，`docker-compose` 单容器组。

---

## 1. 测量过程与真实数据（照抄即可复现）

```bash
free -m
#               total  used  free  shared  buff/cache  available
# Mem:           1967  1333    98        0         719        634
# Swap:             0     0     0

docker stats --no-stream
# backend    862MiB / 1.921GiB  43.82%   PIDS 17   NET 739MB↓/12.6GB↑   BLOCK 5.38GB读/3.48GB写
# frontend     6.8MiB / 1.921GiB  0.35%             NET 25.5GB↓/26.4GB↑

PID=$(docker inspect -f '{{.State.Pid}}' ds-demos-showcase-backend-1)
grep -E "^(Rss|Anonymous)" /proc/$PID/smaps_rollup
# Rss         740504 kB
# Anonymous   730912 kB        ← 99% 是可写堆，不是映射进来的文件页
grep Threads /proc/$PID/status # Threads: 16
grep '\[heap\]' /proc/$PID/maps
# 55ee7bac1000-55ee7efc3000 rw-p ... [heap]   ← 跨度 0x4502000 ≈ 69MB（主堆很小）
wc -l < /proc/$PID/maps        # 648
```

**决定性的一条**（把最大的匿名可写映射段列出来）：

```bash
while read -r rng perm o d i p; do
  s=$((0x${rng%-*})); e=$((0x${rng#*-})); sz=$((e-s))
  [ -z "$p" ] && [ "$perm" = "rw-p" ] && echo $sz
done < /proc/$PID/maps | sort -rn | head -12
# 65859584 / 62066688 / 59064320 / 58466304 / 57499648 / 54415360
# 52916224 / 51859456 / 44691456 / 42582016 / 34480128 / 31612928     ← 合计 ≈ 645MB
```

## 2. 判读：为什么这组数字唯一指向 arena

| 观测 | 推论 |
|---|---|
| `Anonymous ≈ Rss`（730≈740MB） | 全是可写堆 → 排除"mmap 了 demo 文件/SQLite 页"、排除线程栈、排除 shmem/tmpfs（`shared 0`） |
| `[heap]` 只有 **69MB**，但匿名堆 **730MB** | 660MB 不在主堆里 → 分散在别的 mmap 段 |
| 那些段是 **12 段 × 30~64MB**（不是 1 段几百 MB） | **arena 碎片的独有指纹**。若是真·活对象驻留，形态会是一个被撑大的主堆/单个巨段 |
| 段大小 31/34/42/44/51/54/57/58/59/62/63MB（各不相同） | glibc arena heap 以 64MB 预留、按各线程历史峰值增长 —— 每格都被不同线程撑到过 |
| `17 PIDS` / `Threads: 16` | 单 worker，但内部有大量线程（anyio 线程池 ≤40、`asyncio.to_thread`、`oss_sync` 后台线程、`visits` flusher）→ 足以占满 `8×CPU` 个 arena 名额 |

**为什么"只涨不跌、重启归零、形态是平滑斜线"**：arena 之间无法合并，且 `brk` 只能砍段顶 → 每条线程"干过一次重活"就把自己那格永久撑大。不同线程轮转处理上传/预览/同步，叠加起来就是一条单调上升的斜线，而不是一次阶跃。

## 3. 被这次测量推翻/降级的假设（记下来免得下次重走）

| 假设 | 结论 | 依据 |
|---|---|---|
| 面板把 page cache 算进"已用"，是虚警 | ❌ **推翻** | `buff/cache 719MB` 确实可回收，但 `used 1333MB` 里 backend 自己占 862MiB —— 涨在进程内，是真的 |
| B1：9 个 IP 键限流表永不删 key（`stats.py:19,48`、`demos.py:42`、`forum.py:35`、`sessions.py:20`、`ratings.py:23,24`、`tags.py:38`） | ⚠️ **是真 bug，但不是本次原因** | 这些表**全部只挂在 POST/写动作上**（页面打点、心跳、评分、上传、会话日志、标签申请），不挂 GET。key 基数 = 唯一"发过请求的访客 IP"，要吃到 660MB 需要 ~30 万唯一 IP。→ 降级为"顺手清理" |
| B2：`_RELATED_CACHE`（`demos.py:60`）过期条目永不淘汰，value 是 30 个完整序列化 demo | ⚠️ 真 bug，量级几十 MB | 增长与"被点过相关推荐的不同 slug 数"成正比，会平台化 |
| 上传临时文件落在 tmpfs | ❌ 排除 | `shared 0` |
| 17 条线程的栈 | ❌ 排除 | 虚拟 8MB/条，实touch 约 KB 级 |
| SQLite 20 连接 × 2MB 页缓存 | 只抬基线（~40MB），有界 | 解释不了 660MB |

## 4. 方法论（下次 30 秒定位，不用来回读代码）

三条命令就能把「page cache 虚警 / 进程真涨 / 涨在 arena 还是活对象」分干净：

```bash
# ① 是系统口径还是进程？看 available 与 docker stats
free -m && docker stats --no-stream
# ② 是活对象还是分配器？主堆 vs 分散段
PID=$(docker inspect -f '{{.State.Pid}}' <容器名>)
grep -E "^(Rss|Anonymous)" /proc/$PID/smaps_rollup; grep '\[heap\]' /proc/$PID/maps
# ③ 段形状（本文件 §1 最后那条 awk/while 脚本）→ 一排 64MB 级散段 = arena
```

> **教训**：`used%` 高 ≠ 应用有问题；但 `docker stats` 里进程 RSS 高 ≠ 泄漏。**必须看到"主堆 vs 分散段"的形状才允许下结论**。本次我第一版分析就把 B1 限流表排得过高（它只挂 POST，不挂 GET），是这条命令序列把它降回原形的。

## 5. 已推的修复（`docker-compose.yml`，纯配置零代码）

```yaml
services:
  backend:
    environment:
      MALLOC_ARENA_MAX: "2"          # ← 核心：从 8×CPU 压到 2，free 的内存可合并并可被 trim 回收
      MALLOC_TRIM_THRESHOLD_: "131072"
    mem_limit: 768m                  # 有天花板：宁可被限制并暴露，不拖死全机（含 docker build 自身）
    logging: { driver: json-file, options: { max-size: "20m", max-file: "5" } }
  frontend:
    logging: { driver: json-file, options: { max-size: "20m", max-file: "5" } }   # nginx 每请求一条 access log，是宿主磁盘最大的一块写
```

部署（**改环境变量必须重建容器，`restart` 不重读** —— 见 `运维经验与排坑记录.md` §1.1）：

```bash
cd /opt/ds-demos-showcase && git pull
docker compose up -d --force-recreate backend frontend
```

**预期**：RSS 从 862MiB 掉到 **150~250MiB** 并稳住；`free -m` 的 used 从 ~68% 降到 ~30%。
**代价**：malloc 锁竞争略升（当前 CPU ~1%，可忽略）。

验证生效（同 §1 第三条命令，应该只剩 1~3 个大段）：

```bash
PID=$(docker inspect -f '{{.State.Pid}}' ds-demos-showcase-backend-1)
while read -r rng perm o d i p; do
  s=$((0x${rng%-*})); e=$((0x${rng#*-})); sz=$((e-s))
  [ -z "$p" ] && [ "$perm" = "rw-p" ] && echo $sz
done < /proc/$PID/maps | sort -rn | head -8
```

### 实测结果（2026-09-02 部署后，确认有效）

```bash
free -m
#               total   used   free  shared  buff/cache  available
# 修复前         1967   1333     98        0         719        634    ← used 68%
# 修复后         1967    710    822        0         618       1256    ← used 36% / available 1256MB
```

最大的匿名可写段（同一命令，修复前 → 修复后）：

```
修复前：65859584 62066688 59064320 58466304 57499648 54415360 52916224 51859456 …（12 段 ≈ 645MB）
修复后：11866112 10485760 10485760  9437184  8388608  8388608  8388608  8388608
```

**形态判读的收官**：修复后最大的段变成了 **8388608 = 正好 8MiB** —— 那是 CPython `pymalloc` 的 ARENA_SIZE，一个健康 Python 进程本来就该长这样。修复前那些 30~64MB 的 glibc arena heap 全部消失。**诊断与修复同时被证实。**

系统层回收 `1333 - 710 = 623MB`（全部来自 backend 进程），即容器 RSS 从 862MiB 降到 **约 240MiB**，落在预测的 150~250MiB 区间内。CPU 无可见退化。

> **后续观察口径**：`mem_limit=768m` 已生效，所以"再涨"会被限制在 768m 内而不是拖死机器。
> 若 24h 内又**线性**爬回 500MB+（而不是升到 ~300MB 就平台化），说明还有真·活对象驻留 → 优先查 §6.3/§6.4（B1 限流表、B2 `_RELATED_CACHE`），并按 §6.5 上 `/admin/mem` 接口定位。

若压完 arena 之后**仍有可观爬升**：上 jemalloc（Dockerfile 装 `libjemalloc2` + `ENV LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2`），它对脏页归还比 glibc 积极，是小机型跑 Python Web 的标配。

## 6. 遗留风险（这次没动，按危险度排序）

1. 🔴 **`swap 0` + 上传整包读进内存** —— `_read_limited`（`routers/demos.py:185`）是 `data = await file.read()` **先全读进 RAM 再判 413**，上限 200MB；一次上传实际峰值 400~600MB（原 bytes + zipfile + `io.BytesIO` 重打包），而 `available` 只有 634MB。**这是随时会 OOM 杀 backend 的真雷。**
   根治：`_read_limited` 改分块 `await file.read(1<<20)` 边读边限；`max_upload_size` 降到 50MB（AI 网页 demo 完全够）。
   *（本次未做：`demos.py` 工作区里有别人未提交的 v2 改动，动它会打架。）*
2. 🟠 **建议加 2G swap 兜底**（2G 机型标配，防"一次大上传 = 进程被杀"）：
   ```bash
   fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
   echo '/swapfile none swap sw 0 0' >> /etc/fstab
   ```
3. 🟡 **B1 限流表永不删 key** —— 统一换成有界 + 定期清扫的窗口容器（一处实现，9 处受益），顺手修掉"`defaultdict` 一读就建 key"。
4. 🟡 **B2 `_RELATED_CACHE` 无淘汰** —— 换 `TTLCache(maxsize, ttl=60)`，或只缓存 slug 列表不缓存整份序列化对象。
5. 🟡 **缺可观测性**：本次全靠"登录服务器敲命令"才定案。应加一个 admin-only `GET /admin/mem`：`VmRSS/VmData` + 各限流表 `len()` + `_RELATED_CACHE` 条目数 + `engine.pool.status()` + `gc` top 类型。**有了它，这类问题一次 curl 就定位。**
6. ⚪ 提示：`backend NET ↑12.6GB` vs `frontend NET ↑26.4GB` —— 一半出站流量是从 Python 进程读文件吐出去的（`OSS_SERVE_LOCAL=true`）。这是刻意的省钱选择（OSS 只作备份），但它同时也是 arena 被撑大的燃料；若要再压内存/降负载，考虑把预览子资源整体切到 OSS+CDN（配合已上的版本化 URL，缓存失效已不成问题）。
