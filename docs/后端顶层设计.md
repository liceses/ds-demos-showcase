# 后端顶层设计

> 目标：在现有 FastAPI + SQLAlchemy + SQLite 单机架构上，建立**健壮、可维护、可读**的工程基线，
> 支撑论坛、通知、评分、标签等持续演进。

## 一、分层架构

```
app/
├── main.py            # 入口：中间件、路由注册、启动迁移/种子
├── config.py          # 配置（pydantic-settings，环境变量注入）
├── database.py        # engine / SessionLocal / Base / PRAGMA
├── models.py          # ORM 模型（薄，只放字段/关系）
├── schemas.py         # Pydantic 请求/响应（契约）
├── deps.py            # 依赖：current_user / require_admin / require_agent / 限流
├── security.py        # JWT / 密码 / 签名 / Cookie
├── serializers.py     # 序列化（复杂输出；简单输出直接 schema）
├── routers/           # HTTP 层：参数解析 + 鉴权 + 调 service，不写业务
│   ├── demos.py / tags.py / forum.py / notifications.py / ...
├── services/          # 业务层：核心逻辑、事务、外部调用
│   ├── demo_service.py / tag_service.py / forum_service.py
│   ├── notification_service.py / rating_service.py / ...
├── utils/             # 通用：rate_limit / link_validate / pagination / slug
└── tests/             # pytest：service 单测 + 接口冒烟
```

### 职责边界
| 层 | 做什么 | 不做什么 |
|---|---|---|
| router | 参数校验、鉴权、调 service、返回 | 不直接写 ORM、不写业务规则 |
| service | 业务规则、事务、外部调用、通知触发 | 不解析 HTTP、不拼响应结构 |
| models | 字段/关系/约束 | 不写业务方法（可放少量属性） |
| schemas | 输入输出契约 | 不写逻辑 |

## 二、健壮性

1. **统一错误**：`HTTPException` + 统一 `{detail, code}`；业务异常用 `AppError(code, message, status)` 封装，router 层捕获转 HTTP。
2. **外部调用降级**：OSS / models.dev / 通知等失败**不阻塞主流程**（try/except + 日志 + 降级本地/静默）。
3. **事务边界**：写操作在 service 内一个事务完成（如评分冗余列、论坛 reply_count、标签合并）；失败回滚。
4. **后台任务隔离**：统计落库、通知发送等用线程/队列，避免拖慢请求。
5. **输入校验**：Pydantic 强类型 + 长度/枚举/正则；链接校验（http/https、内网/回环/保留地址、域名黑名单）。
6. **安全**：JWT（Cookie+Bearer）、限流（用户+IP 双维）、SSRF 防护、Markdown 只存原文（前端消毒）、保留 key 保护。
7. **幂等**：上传幂等键、标签合并 dry_run、迁移脚本 source_comment_id 去重。

## 三、可维护性

1. **路由薄、服务厚**：业务逻辑集中在 service，路由只做 HTTP 翻译。
2. **配置集中**：所有可配项进 `config.py`（环境变量），不散落硬编码；`.env.example` 同步。
3. **迁移策略**：`_ensure_*_columns` 增量迁移 + `create_all`；未来换 PostgreSQL 时切 Alembic。
4. **模块单一职责**：一个 service 管一个领域（demo/tag/forum/notification/rating）。
5. **命名一致**：snake_case、动词开头（create/update/delete/list）、常量大写集中。
6. **文档同步**：`API_CONTRACT.md`（契约）、`backend-design.md`（实现）、`docs/`（专项设计）随代码更新。

## 四、可读性

1. **类型注解**：全量 `Mapped[...]` / `->` 返回类型。
2. **docstring**：每个 router/service 函数说明用途、参数、副作用。
3. **避免魔法数字**：限流阈值、窗口、大小上限进常量/配置。
4. **小函数**：一个函数只做一件事；复杂流程拆 helper（如 `_recalc_*`、`_validate_*`）。
5. **注释解释「为什么」**，不解释「是什么」。

## 五、数据访问

- 小项目**不强制 repository 层**：service 内直接 SQLAlchemy query，但查询封装成私有函数，避免散落。
- 冗余列（rating_sum/count、forum reply_count）由 service 事务维护，**不靠定时重算**（除迁移/修复脚本）。
- 分页统一 `Paginated` schema + `page/page_size`。

## 六、通知/论坛扩展设计

- **通知**：`notification_service.create(user_id, type, actor_id, demo_slug?, topic_id?, reply_id?)` 在业务动作后调用；**失败静默**，不阻塞主流程。
- **论坛**：`forum_service` 统一处理发帖/回复/审核/举报/合并；事务内更新 `reply_count/status`；`parent_id` 支持嵌套。
- **反应/声望**：已落地 `community_service`（forum_reactions + users.reputation，赞 +1/感谢 +2，取消扣回；通知 `forum_reaction`）。
- **关注**：已落地 `community_service`（user_follows + 用户主页聚合 + `/forum/topics?followed=1`）。

## 七、测试

- pytest + FastAPI TestClient，测试放 `backend/tests/`。
- 已覆盖核心路径：发帖审核→通过→回复→通知→锁定 403、赞/感谢/声望/关注、评分聚合/撤分。
- 数据库用临时 SQLite（`backend/tests/conftest.py` 在导入 app 前注入 `DATABASE_URL`，避免污染真实库）。
- 运行：`cd backend && pip install -r requirements-dev.txt && python -m pytest tests -v`。

## 八、实施建议（按此演进）

1. **先立骨架**：把现有 router 里的业务逻辑逐步抽到 service（不一次重构，随改随抽）。
2. **加统一错误/日志**：`AppError` + 请求日志中间件。
3. **通知系统**：按 `notification_service` 落地，动作点埋通知。
4. **论坛互动**：`parent_id`/分页/排序/锁定/已解决，全部走 `forum_service`。
5. **社区互动**：`community_service` 落地赞/感谢、声望、关注、用户主页聚合。
6. **测试**：核心路径补 pytest。
