## 1. Docker 与部署

### 1.1 改 `.env` 必须重建容器，`restart` 不重读环境变量
- **现象**：注释掉 `.env` 里的 `OSS_CUSTOM_DOMAIN` 后 `docker compose restart backend`，下载/预览仍走旧域名。
- **原因**：容器创建时把 `.env` 值固化进环境变量，`restart` 不重新解析 `.env`。
- **修复**：改完 `.env` 一律 `docker compose up -d backend`（重建）。纯重启（不改环境变量）才用 `restart`。
- **验证**：`docker compose exec backend env | grep OSS_CUSTOM_DOMAIN` 应为空/新值。

### 1.2 后端 502 排查套路
- **现象**：`/api/v1/*` 全部 502，前端静态页正常。
- **原因**：nginx 正常、后端容器挂了/重启循环（`docker compose ps` 里 backend 没有 `Up`）。
- **套路**：
  ```bash
  docker compose ps          # backend 是否 Up
  docker compose logs backend --tail 80   # 看启动崩溃原因
  df -h                      # 磁盘是否打满
  ```
- 常见崩溃：启动期 OSS 上传抛异常（见 2.1）、数据库锁、磁盘满。

### 1.3 后端容器里没有 git
- 曾因发布调用 `git commit` 在无 git 容器里报 503；已移除每 demo git，改轻量时间线 + 公告。
- 教训：容器内依赖（git/系统包）改动要进 Dockerfile 并重建验证，不能假设宿主有。

## 2. OSS 与对象存储

### 2.1 `UserDisable` 403 = RAM 用户被禁用（不是 Key 过期）
- **现象**：后端启动即崩，日志 `oss2.exceptions.ServerError: {"Code": "UserDisable", "EC": "0003-0000e801"}`。
- **原因**：OSS AccessKey 所属的**阿里云 RAM 用户被禁用**（可能手动禁用，或安全中心检测到 Key 泄露自动禁用）。
- **修复**：RAM 控制台启用该用户，或新建 AccessKey 更新 `.env`。
- **预防**：AK/SK 绝不能进 git/公开仓库（本项目 SK 曾进过 git，被建议轮换）。

### 2.2 OSS 不可用不能阻塞站点
- 已实现三层兜底：
  1. 启动期默认封面上传失败 → 只警告不崩（`main.py` try/except）；
  2. 发布时 OSS 上传失败 → 降级本地存储（`_oss_upload_safe`），页面仍可访问；
  3. **启动自动同步**（`services/oss_sync.py`，幂等）+ 管理后台「同步本地文件到 OSS」按钮。
- **自动同步思路**：以 `demos/{slug}/{slug}.zip` 在 OSS 是否存在作为「该 demo 已同步」标记；缺失才补传文件/会话/zip，封面按 key 缺失才传。第一次全量，之后每次启动只发 HEAD 检查（秒级）。
- **边界**：若某次上传中途失败（zip 已传、文件半途），标记存在会跳过 → 少量缺失；可手动点按钮/重启兜底。

### 2.3 资源存在性检查用 HEAD，不要全量下载
- **现象**：页面刷新白图、加载半天。
- **原因**：用 `oss.get_bytes()`（GET 全量下载对象）判断存在性，等于每个资源服务器都完整拉一遍再 307 给浏览器 → 双倍流量 + 慢。
- **修复**：改 `oss.object_exists()`（HEAD，几字节）。`oss.py` 已提供 `object_exists()`。
- **预防**：所有「只看有没有」的场景禁止用 get_bytes。

### 2.4 大陆地域 OSS 绑定自定义域名必须备案
- **现象**：OSS 控制台绑定 `cdn.deepdemos.top` 提示需要 ICP 备案。
- **结论**：无备案的香港服务器场景，OSS 自定义域名绑定走不通。
- **免费 CDN 替代**：Cloudflare Worker 反代（回源 OSS 默认域名，免备案免证书）——代码见项目讨论记录；或干脆 OSS 默认域名直连 + 买「下行流量包」（地域选华北2/北京）。
- **`NonCnameForbidden` 403**：Cloudflare 直接 CNAME 到 OSS 且未绑定时，OSS 因 Host 未绑定拒绝（`The host in request is not bound in OSS`）——免费版无法改回源 Host，此路不通。

### 2.5 历史对象没有缓存头
- 新增缓存头只对**之后上传/同步**的对象生效；历史对象需重新上传覆盖，或用 ossutil 批量改（`ossutil set-meta`）。

## 3. 缓存与 CDN

### 3.1 重定向（307/302）不要设长缓存，更不要 immutable
- **现象**：改配置后封面仍指向旧域名，裂了一天。
- **原因**：`/media` 307 曾设 `Cache-Control: public, max-age=86400, immutable`，被 Cloudflare/浏览器缓存；目标地址随 `OSS_CUSTOM_DOMAIN` 变化时旧缓存依然生效。
- **修复**：`/media` 重定向改 `no-store`；**最终对象**（OSS 文件）才设 immutable 长缓存。
- **原则**：可变的跳转不缓存，不可变的内容缓存。

### 3.2 Cloudflare 改配置后要 Purge
- **现象**：后端/环境变量已改，资源仍走旧地址。
- **判断**：响应头 `server: cloudflare` + `age: N` 说明是 CF 缓存。
- **修复**：Cloudflare → Caching → Purge Everything（免费版可用）。
- **预防**：所有 3xx 重定向不缓存后（见 3.1），此类问题不再复发。

### 3.3 「不缓存重定向」不会增加流量
- 浏览器缓存的是**最终图片对象**（immutable 1 天），刷新不重复下载；重定向本身几百字节，no-store 的代价可忽略。

## 4. 性能

### 4.1 上传请求超时 15s 不够
- **现象**：上传 demo 报 `timeout of 15000 ms exceeded`（文件很小也报）。
- **原因**：axios 默认 15s；发布要解压 + 逐文件传 OSS + 封面，容易超时。
- **修复**：create/update demo 单独 `{ timeout: 120000 }`（`frontend/src/api/index.ts`）。

### 4.2 SQLite 并发写
- 已配置 `journal_mode=WAL`、`busy_timeout=5000`、`synchronous=NORMAL`（`backend/app/database.py`）；生产 uvicorn 单 worker，避免多进程写锁。

### 4.3 上传重活阻塞事件循环 → 批量上传把整站拖"半死"（只出顶栏）
- **现象**：AI agent 一口气传很多 demo 后，页面只剩顶栏，`GET /demos` 列表 20s+ 超时，其余接口（公告/标签/详情）却正常。
- **根因**：上传端点为 `async def`，但解压 zip、逐文件传 OSS、URL 下载、存封面都是**同步阻塞调用**，直接跑在事件循环线程上；批量上传占满事件循环 → 依赖事件循环的请求排队卡死，而列表（sync `def`，走线程池）也因 SQLite 写锁/排队打满超时，前端 SPA 只渲染出顶栏。
- **修复**（`demos.py`，commit 1629437）：把阻塞重活统一 `await asyncio.to_thread(...)` 丢线程池执行，DB 操作留在主线程（SQLAlchemy Session 非线程安全，勿整段搬线程）：
  - `storage.extract_zip` / `storage.save_cover` / `_oss_upload_safe` → 线程池
  - `create_demo_from_url` 的 URL 下载（`_download_url_bytes`）→ 线程池，且封面限额用 `settings.max_upload_size`（默认 200MB；`max_cover_size` 是未使用的死配置）
  - `update_demo` 的解压/OSS/封面 → 线程池
- **例外**：`_snapshot_demo`（保留旧版本）同时碰 DB 与文件复制，属低频手动路径，暂未线程化；日后若卡再拆。
- **排查确认**：先确认 `GET /demos` 超时但其它接口 OK（见 §8 探测套路），再上服务器看 `docker compose logs / stats`。
- **预防**：上传类端点内**任何**"解压/网络/OSS/大文件"操作必须丢线程池；别再写同步阻塞进 async 端点。

### 4.4 单 worker 内存态：现状清单与扩容触发条件（架构权衡，非 bug）

Dockerfile 固定 `--workers 1`，以下状态只存在于进程内存，不落库、不共享：

| 状态 | 位置 | 重启丢失后果 |
|---|---|---|
| 未落库 PV（30s 落库窗口） | `visits.py::_today_count` | 丢最多 30 秒 PV |
| 近 10 分钟 PV 时间戳 | `visits.py::_recent_hits` | 实时数归零，30s 后自愈 |
| 在线表 | `visits.py::_online` | 在线人数清零 |
| 限流字典 ×6 | demos(匿名上传)/sessions/forum/ratings/stats/tags | 所有限流桶清空（≈免费解封，桶很快重积累） |
| 相关推荐/首页随机池/git 缓存 | `demos.py` / `site_git.py`（60s TTL） | 冷启动重算，无感 |

**为什么单 worker**：SQLite 单写（WAL 缓解读、不缓解写）+ 小服务器零依赖，见 §4.2。

**开多 worker 前必读——三处会坏的地方**：
1. 限流额度按进程数翻倍：各 worker 各记各的账，限制 20/小时实际能打 20×N；
2. 在线数/近 1 分钟 PV 系统性偏低：心跳被 round-robin 拆到多个进程，各自只看到一半；
3. PV 落库竞态丢数据：`_flush_locked` 是「读出 → 加 → 写回」，多进程同时 flush 时后写覆盖先写（单进程有 `_lock` 无此问题）。

**扩容触发条件（任一出现才动手，不预先施工）**：需要多 worker / 第二台机器；限流滥用需要重启也清不掉的封禁；需要对实时统计做精确承诺。

**迁移顺序（按收益）**：① 限流 → Redis（`INCR + EXPIRE`，做完才能安全开多 worker）→ ② 在线表 → Redis TTL 键 → ③ PV 落库改原子 SQL（`UPDATE visit_daily SET count = count + :delta`，一行改动，可提前做、多 worker 必需）→ ④ 推荐缓存/随机池/git 缓存不用动（各进程各存一份无正确性问题）。

## 5. 数据与迁移

### 5.1 SQLite `create_all` 不会改旧表
- **现象**：加了新列后旧库启动没新字段。
- **修复**：`main.py::_ensure_demo_columns()` 用 `ALTER TABLE ... ADD COLUMN` 增量补列（demo_type/external_url/prompt/video_url/guest_name/rating_* 等）。
- **预防**：以后加列必须同步更新该函数。（2026-08-28 复核：`updated_at` 列此前曾漏，**现已补进** additions 清单，旧库可自动加列。）

### 5.2 历史字段读时归一，不删数据
- 例：`guest_name`（匿名昵称）已废弃，列保留但**读时忽略**，匿名作者恒为 `public`，历史数据无需迁移。

### 5.3 只定义迁移函数不调用 = 启动必崩（forum_topics.locked）
- **现象**：后端启动反复 `sqlite3.OperationalError: no such column: forum_topics.locked`，`_seed_forum_notice()` 里 ORM 查询 ForumTopic 就崩。
- **原因**：`_ensure_forum_columns()` 已写好（给旧 `forum_topics` 补 `locked`/`solved`），但 `init_db()` 里**漏了调用**，只调了 `_ensure_forum_reply_columns()`；旧库没补列，而 ORM 会 SELECT 模型全字段 → 启动即炸。
- **修复**：`init_db()` 中在 `_seed_forum_notice()` 前调用 `_ensure_forum_columns()`（commit `f4e51ad`）。
- **预防**：新增模型列后，除了写 `_ensure_*_columns()`，还要在 `init_db()` 里**实际调用**；提交前 grep `def _ensure_` 与 `init_db` 里的调用是否一一对应。

## 9. Python 模块级变量：函数内赋值必须 `global`（踩了 2 次）

### 现象
- 第一次：`visits.record_visit()` 里 `_today_count += 1` → `UnboundLocalError` → 首页/作品库 500。
- 第二次：`visits._flush_locked()` 里 `_today_count = 0`（落库后清零）→ 函数开头 `if _today_count == 0` 就 `UnboundLocalError` → 跨天触发 `/stats/live` 500。

### 原因
Python 规则：**函数内只要对某个名字赋值（含 `+=`、`=`），该名字在整个函数内都被视为局部变量**，即使模块级已有同名全局变量。读取发生在赋值之前就会 `UnboundLocalError`。

### 修复
```python
def record_visit(...):
    global _today_count   # 赋值前必须声明
    _today_count += 1

def _flush_locked():
    global _today_count   # 函数内有 `_today_count = 0`，必须声明
    if _today_count == 0:
        return
    ...
    _today_count = 0
```

### 预防清单
- 函数内**只读**模块级变量：不需要 `global`。
- 函数内**赋值/增强赋值**（`=`、`+=`、`-=`）模块级变量：**必须**在函数开头 `global 变量名`。
- 改这类「内存统计/缓存」模块时，写完先 `python -m compileall` 不够（编译查不出），要**实际调用一次该函数**验证；或直接跑 `python -c "from app.services.visits import *; record_visit(); _flush_locked()"` 类冒烟。
- 后台线程里的异常常被 `try/except` 吞掉，页面不炸但功能静默失效——**日志里看到 UnboundLocalError 先查 global**。

## 10. 线上实测快照（2026-08-28，deepdemos.top）

> 对线上的一次只读探测记录（API/预览/下载请求），固化当天的实际行为基线，供后续排障对照。

### 10.1 存储与 CDN
- **`OSS_SERVE_LOCAL=true`（默认本地服务模式）在线上生效**：实测预览子资源（js/css）、zip 下载、`/media` 封面均由源站 **200 直出**，无 302 到 OSS；OSS 实际只承担双写备份 + 会话日志。带宽大头由 Cloudflare 边缘缓存挡（版本化预览 URL 与封面均为 `Cache-Control: public, max-age=86400, immutable`）。
- 全站 **https 由 Cloudflare 边缘提供**（响应头 `Server: cloudflare`），源站 nginx 仅监听 80、回源 http。

### 10.2 已观察到的行为问题（待处理，详见下）
- **IP 取值口径割裂**：uvicorn 未信任 Docker 网段来的 `X-Forwarded-For` → `demos.py`（匿名上传限流）与 `sessions.py`（会话日志限流）里的 `request.client.host` 恒为 **nginx 容器 IP**，等于全站共享一个限流桶；而 `forum/ratings/stats/tags` 读 **XFF 首段**——Cloudflare 链路下客户端可自带伪造 XFF（真实 IP 被 CF 追加在后面），限流与匿名评分指纹可被头部绕过。两套口径并存，需统一。
  - **（2026-08-28 代码已修复，随下次部署生效）**：新增 `backend/app/client_ip.py::get_client_ip`，统一按 **CF-Connecting-IP → X-Real-IP → client.host** 优先级取值（头值做 ipaddress 格式校验，非法逐级回落）；demos / sessions / forum / ratings / stats×4 / tags 七处调用点全部替换，`X-Forwarded-For` 全面弃用；请求日志加 `ip=` 字段便于上线验证。残余风险：绕过 CF 直连源站时 CF 头可伪造（必要时用 nginx realip 模块 + CF 网段收紧）。
- **JWT Cookie 无 `Secure` 标志**：后端以 `request.url.scheme == "https"` 判定，回源 http 恒为 false。有 `httponly + samesite=lax` 兜底。（2026-08-29 已修：新增 `COOKIE_SECURE` 配置 + `X-Forwarded-Proto` 兜底判定，生产 `.env` 设 `true` 即可；见 `.env.example`。）
- **PV 异常峰值（✅ 已定性，勿再误诊为刷量）**：2026-08-22/23 出现 292 万 / 189 万 PV 峰值（正常日约 0.9~3 万），`GET /stats/visits` 的 `total`（487 万）约 99% 来自这两天。**经站长确认：根因是统计方法 bug，不是脚本刷量；统计口径已改正（2026-08）**，`total` 失真是 bug 的结果而非滥用证据。
  - **教训**：以后看到 PV 尖峰，第一步先核对统计口径本身（打点触发次数、聚合/累加逻辑、去重规则），确认统计方法无 bug 之后再考虑滥用；限流可绕过（见下条 XFF 问题）是独立的加固项，不能作为「被刷了」的证据。

## 11. 前端类型检查双门槛：`vue-tsc --noEmit` 是弱检查，`npm run build`（`vue-tsc -b`）才是真门槛

- **现象**：本地 `npm run typecheck`（`vue-tsc --noEmit`）通过，推上服务器后 Docker 构建 `npm run build` 报 TS 错误（TS2538 `Type 'undefined' cannot be used as an index type`，`mock.ts` 里拿可空的 `demo_type` 直接做索引键），前端镜像构建失败。
- **根因**：`frontend/tsconfig.json` 是 **solution 式**文件——`"files": []` + 只有 `references` 指向 `tsconfig.app.json` / `tsconfig.node.json`。`vue-tsc --noEmit` 不带 `-b` 时只检查 solution 根（没有任何文件）→ **近乎空跑**；而 `npm run build` = `vue-tsc -b && vite build`，`-b` 才会沿 references 真正逐项目检查。两个命令的检查强度完全不同，`typecheck` 绿 ≠ 构建能过。
- **修复**：`mock.ts` 的 `demos_by_type` reduce 前先 `const t = d.demo_type || 'web'` 判空（commit `3295a1d`）。
- **预防**：
  1. 本地验证**一律用 `npm run build`**——与 Dockerfile 内逐字相同的命令，过了它等于过了服务器那关；`typecheck` 脚本只能当快速参考，不可作为发布门槛。
  2. 涉及 TS 类型收窄的写法（可空字段做索引键、`arr[0].x` 无判空等）按 `-b` 模式的严格度写，别按 `--noEmit` 的体感写。
  3. 以后若想修 `typecheck` 脚本本身，可改为 `vue-tsc -b`（改完先跑一次真实构建确认 composite 配置兼容）。
- **关联教训**：与 §4.1「本地验证要用客户端真实路径」同源——**验证环境与发布环境不一致 = 检查等于没做**。
