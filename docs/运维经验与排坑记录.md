## 1. Docker 与部署

### 1.1 改 `.env` 必须重建容器，`restart` 不重读环境变量
- **现象**：注释掉 `.env` 里的 `OSS_CUSTOM_DOMAIN` 后 `docker compose restart backend`，下载/预览仍走旧域名。
- **原因**：容器创建时把 `.env` 值固化进环境变量，`restart` 不重新解析 `.env`。
- **修复**：改完 `.env` 一律 `docker compose up -d backend`（重建）。纯重启（不改环境变量）才用 `restart`。
- **验证**：`docker compose exec backend env | grep OSS_CUSTOM_DOMAIN` 应为空/新值。

### 1.2 后端 502 排查套路
- **现象**：`/api/v1/*` 全部 502，前端静态页正常。
- **原因**：nginx 正常、后端容器挂了/重启循环（`docker compose ps` 里 backend 没有 `Up`）。
- **套路**：
  ```bash
  docker compose ps          # backend 是否 Up
  docker compose logs backend --tail 80   # 看启动崩溃原因
  df -h                      # 磁盘是否打满
  ```
- 常见崩溃：启动期 OSS 上传抛异常（见 2.1）、数据库锁、磁盘满。

### 1.3 后端容器里没有 git
- 曾因发布调用 `git commit` 在无 git 容器里报 503；已移除每 demo git，改轻量时间线 + 公告。
- 教训：容器内依赖（git/系统包）改动要进 Dockerfile 并重建验证，不能假设宿主有。

## 2. OSS 与对象存储

### 2.1 `UserDisable` 403 = RAM 用户被禁用（不是 Key 过期）
- **现象**：后端启动即崩，日志 `oss2.exceptions.ServerError: {"Code": "UserDisable", "EC": "0003-0000e801"}`。
- **原因**：OSS AccessKey 所属的**阿里云 RAM 用户被禁用**（可能手动禁用，或安全中心检测到 Key 泄露自动禁用）。
- **修复**：RAM 控制台启用该用户，或新建 AccessKey 更新 `.env`。
- **预防**：AK/SK 绝不能进 git/公开仓库（本项目 SK 曾进过 git，被建议轮换）。

### 2.2 OSS 不可用不能阻塞站点
- 已实现三层兜底：
  1. 启动期默认封面上传失败 → 只警告不崩（`main.py` try/except）；
  2. 发布时 OSS 上传失败 → 降级本地存储（`_oss_upload_safe`），页面仍可访问；
  3. **启动自动同步**（`services/oss_sync.py`，幂等）+ 管理后台「同步本地文件到 OSS」按钮。
- **自动同步思路**：以 `demos/{slug}/{slug}.zip` 在 OSS 是否存在作为「该 demo 已同步」标记；缺失才补传文件/会话/zip，封面按 key 缺失才传。第一次全量，之后每次启动只发 HEAD 检查（秒级）。
- **边界**：若某次上传中途失败（zip 已传、文件半途），标记存在会跳过 → 少量缺失；可手动点按钮/重启兜底。

### 2.3 资源存在性检查用 HEAD，不要全量下载
- **现象**：页面刷新白图、加载半天。
- **原因**：用 `oss.get_bytes()`（GET 全量下载对象）判断存在性，等于每个资源服务器都完整拉一遍再 307 给浏览器 → 双倍流量 + 慢。
- **修复**：改 `oss.object_exists()`（HEAD，几字节）。`oss.py` 已提供 `object_exists()`。
- **预防**：所有「只看有没有」的场景禁止用 get_bytes。

### 2.4 大陆地域 OSS 绑定自定义域名必须备案
- **现象**：OSS 控制台绑定 `cdn.deepdemos.top` 提示需要 ICP 备案。
- **结论**：无备案的香港服务器场景，OSS 自定义域名绑定走不通。
- **免费 CDN 替代**：Cloudflare Worker 反代（回源 OSS 默认域名，免备案免证书）——代码见项目讨论记录；或干脆 OSS 默认域名直连 + 买「下行流量包」（地域选华北2/北京）。
- **`NonCnameForbidden` 403**：Cloudflare 直接 CNAME 到 OSS 且未绑定时，OSS 因 Host 未绑定拒绝（`The host in request is not bound in OSS`）——免费版无法改回源 Host，此路不通。

### 2.5 历史对象没有缓存头
- 新增缓存头只对**之后上传/同步**的对象生效；历史对象需重新上传覆盖，或用 ossutil 批量改（`ossutil set-meta`）。

## 3. 缓存与 CDN

### 3.1 重定向（307/302）不要设长缓存，更不要 immutable
- **现象**：改配置后封面仍指向旧域名，裂了一天。
- **原因**：`/media` 307 曾设 `Cache-Control: public, max-age=86400, immutable`，被 Cloudflare/浏览器缓存；目标地址随 `OSS_CUSTOM_DOMAIN` 变化时旧缓存依然生效。
- **修复**：`/media` 重定向改 `no-store`；**最终对象**（OSS 文件）才设 immutable 长缓存。
- **原则**：可变的跳转不缓存，不可变的内容缓存。

### 3.2 Cloudflare 改配置后要 Purge
- **现象**：后端/环境变量已改，资源仍走旧地址。
- **判断**：响应头 `server: cloudflare` + `age: N` 说明是 CF 缓存。
- **修复**：Cloudflare → Caching → Purge Everything（免费版可用）。
- **预防**：所有 3xx 重定向不缓存后（见 3.1），此类问题不再复发。

### 3.3 「不缓存重定向」不会增加流量
- 浏览器缓存的是**最终图片对象**（immutable 1 天），刷新不重复下载；重定向本身几百字节，no-store 的代价可忽略。

## 4. 性能

### 4.1 上传请求超时 15s 不够
- **现象**：上传 demo 报 `timeout of 15000 ms exceeded`（文件很小也报）。
- **原因**：axios 默认 15s；发布要解压 + 逐文件传 OSS + 封面，容易超时。
- **修复**：create/update demo 单独 `{ timeout: 120000 }`（`frontend/src/api/index.ts`）。

### 4.2 SQLite 并发写
- 已配置 `journal_mode=WAL`、`busy_timeout=5000`、`synchronous=NORMAL`（`backend/app/database.py`）；生产 uvicorn 单 worker，避免多进程写锁。

### 4.3 上传重活阻塞事件循环 → 批量上传把整站拖"半死"（只出顶栏）
- **现象**：AI agent 一口气传很多 demo 后，页面只剩顶栏，`GET /demos` 列表 20s+ 超时，其余接口（公告/标签/详情）却正常。
- **根因**：上传端点为 `async def`，但解压 zip、逐文件传 OSS、URL 下载、存封面都是**同步阻塞调用**，直接跑在事件循环线程上；批量上传占满事件循环 → 依赖事件循环的请求排队卡死，而列表（sync `def`，走线程池）也因 SQLite 写锁/排队打满超时，前端 SPA 只渲染出顶栏。
- **修复**（`demos.py`，commit 1629437）：把阻塞重活统一 `await asyncio.to_thread(...)` 丢线程池执行，DB 操作留在主线程（SQLAlchemy Session 非线程安全，勿整段搬线程）：
  - `storage.extract_zip` / `storage.save_cover` / `_oss_upload_safe` → 线程池
  - `create_demo_from_url` 的 URL 下载（`_download_url_bytes`）→ 线程池，且封面限额用 `settings.max_upload_size`（默认 200MB；`max_cover_size` 是未使用的死配置）
  - `update_demo` 的解压/OSS/封面 → 线程池
- **例外**：`_snapshot_demo`（保留旧版本）同时碰 DB 与文件复制，属低频手动路径，暂未线程化；日后若卡再拆。
- **排查确认**：先确认 `GET /demos` 超时但其它接口 OK（见 §8 探测套路），再上服务器看 `docker compose logs / stats`。
- **预防**：上传类端点内**任何**"解压/网络/OSS/大文件"操作必须丢线程池；别再写同步阻塞进 async 端点。

### 4.4 单 worker 内存态：现状清单与扩容触发条件（架构权衡，非 bug）

Dockerfile 固定 `--workers 1`，以下状态只存在于进程内存，不落库、不共享：

| 状态 | 位置 | 重启丢失后果 |
|---|---|---|
| 未落库 PV（30s 落库窗口） | `visits.py::_today_count` | 丢最多 30 秒 PV |
| 近 10 分钟 PV 时间戳 | `visits.py::_recent_hits` | 实时数归零，30s 后自愈 |
| 在线表 | `visits.py::_online` | 在线人数清零 |
| 限流字典 ×6 | demos(匿名上传)/sessions/forum/ratings/stats/tags | 所有限流桶清空（≈免费解封，桶很快重积累） |
| 相关推荐/首页随机池/git 缓存 | `demos.py` / `site_git.py`（60s TTL） | 冷启动重算，无感 |

**为什么单 worker**：SQLite 单写（WAL 缓解读、不缓解写）+ 小服务器零依赖，见 §4.2。

**开多 worker 前必读——三处会坏的地方**：
1. 限流额度按进程数翻倍：各 worker 各记各的账，限制 20/小时实际能打 20×N；
2. 在线数/近 1 分钟 PV 系统性偏低：心跳被 round-robin 拆到多个进程，各自只看到一半；
3. PV 落库竞态丢数据：`_flush_locked` 是「读出 → 加 → 写回」，多进程同时 flush 时后写覆盖先写（单进程有 `_lock` 无此问题）。

**扩容触发条件（任一出现才动手，不预先施工）**：需要多 worker / 第二台机器；限流滥用需要重启也清不掉的封禁；需要对实时统计做精确承诺。

**迁移顺序（按收益）**：① 限流 → Redis（`INCR + EXPIRE`，做完才能安全开多 worker）→ ② 在线表 → Redis TTL 键 → ③ PV 落库改原子 SQL（`UPDATE visit_daily SET count = count + :delta`，一行改动，可提前做、多 worker 必需）→ ④ 推荐缓存/随机池/git 缓存不用动（各进程各存一份无正确性问题）。

## 5. 数据与迁移

### 5.1 SQLite `create_all` 不会改旧表
- **现象**：加了新列后旧库启动没新字段。
- **修复**：`main.py::_ensure_demo_columns()` 用 `ALTER TABLE ... ADD COLUMN` 增量补列（demo_type/external_url/prompt/video_url/guest_name/rating_* 等）。
- **预防**：以后加列必须同步更新该函数。（2026-08-28 复核：`updated_at` 列此前曾漏，**现已补进** additions 清单，旧库可自动加列。）

### 5.2 历史字段读时归一，不删数据
- 例：`guest_name`（匿名昵称）已废弃，列保留但**读时忽略**，匿名作者恒为 `public`，历史数据无需迁移。

### 5.3 只定义迁移函数不调用 = 启动必崩（forum_topics.locked）
- **现象**：后端启动反复 `sqlite3.OperationalError: no such column: forum_topics.locked`，`_seed_forum_notice()` 里 ORM 查询 ForumTopic 就崩。
- **原因**：`_ensure_forum_columns()` 已写好（给旧 `forum_topics` 补 `locked`/`solved`），但 `init_db()` 里**漏了调用**，只调了 `_ensure_forum_reply_columns()`；旧库没补列，而 ORM 会 SELECT 模型全字段 → 启动即炸。
- **修复**：`init_db()` 中在 `_seed_forum_notice()` 前调用 `_ensure_forum_columns()`（commit `f4e51ad`）。
- **预防**：新增模型列后，除了写 `_ensure_*_columns()`，还要在 `init_db()` 里**实际调用**；提交前 grep `def _ensure_` 与 `init_db` 里的调用是否一一对应。

## 9. Python 模块级变量：函数内赋值必须 `global`（踩了 2 次）

### 现象
- 第一次：`visits.record_visit()` 里 `_today_count += 1` → `UnboundLocalError` → 首页/作品库 500。
- 第二次：`visits._flush_locked()` 里 `_today_count = 0`（落库后清零）→ 函数开头 `if _today_count == 0` 就 `UnboundLocalError` → 跨天触发 `/stats/live` 500。

### 原因
Python 规则：**函数内只要对某个名字赋值（含 `+=`、`=`），该名字在整个函数内都被视为局部变量**，即使模块级已有同名全局变量。读取发生在赋值之前就会 `UnboundLocalError`。

### 修复
```python
def record_visit(...):
    global _today_count   # 赋值前必须声明
    _today_count += 1

def _flush_locked():
    global _today_count   # 函数内有 `_today_count = 0`，必须声明
    if _today_count == 0:
        return
    ...
    _today_count = 0
```

### 预防清单
- 函数内**只读**模块级变量：不需要 `global`。
- 函数内**赋值/增强赋值**（`=`、`+=`、`-=`）模块级变量：**必须**在函数开头 `global 变量名`。
- 改这类「内存统计/缓存」模块时，写完先 `python -m compileall` 不够（编译查不出），要**实际调用一次该函数**验证；或直接跑 `python -c "from app.services.visits import *; record_visit(); _flush_locked()"` 类冒烟。
- 后台线程里的异常常被 `try/except` 吞掉，页面不炸但功能静默失效——**日志里看到 UnboundLocalError 先查 global**。

## 10. 线上实测快照（2026-08-28，deepdemos.top）

> 对线上的一次只读探测记录（API/预览/下载请求），固化当天的实际行为基线，供后续排障对照。

### 10.1 存储与 CDN
- **`OSS_SERVE_LOCAL=true`（默认本地服务模式）在线上生效**：实测预览子资源（js/css）、zip 下载、`/media` 封面均由源站 **200 直出**，无 302 到 OSS；OSS 实际只承担双写备份 + 会话日志。带宽大头由 Cloudflare 边缘缓存挡（版本化预览 URL 与封面均为 `Cache-Control: public, max-age=86400, immutable`）。
- 全站 **https 由 Cloudflare 边缘提供**（响应头 `Server: cloudflare`），源站 nginx 仅监听 80、回源 http。

### 10.2 已观察到的行为问题（待处理，详见下）
- **IP 取值口径割裂**：uvicorn 未信任 Docker 网段来的 `X-Forwarded-For` → `demos.py`（匿名上传限流）与 `sessions.py`（会话日志限流）里的 `request.client.host` 恒为 **nginx 容器 IP**，等于全站共享一个限流桶；而 `forum/ratings/stats/tags` 读 **XFF 首段**——Cloudflare 链路下客户端可自带伪造 XFF（真实 IP 被 CF 追加在后面），限流与匿名评分指纹可被头部绕过。两套口径并存，需统一。
  - **（2026-08-28 代码已修复，随下次部署生效）**：新增 `backend/app/client_ip.py::get_client_ip`，统一按 **CF-Connecting-IP → X-Real-IP → client.host** 优先级取值（头值做 ipaddress 格式校验，非法逐级回落）；demos / sessions / forum / ratings / stats×4 / tags 七处调用点全部替换，`X-Forwarded-For` 全面弃用；请求日志加 `ip=` 字段便于上线验证。残余风险：绕过 CF 直连源站时 CF 头可伪造（必要时用 nginx realip 模块 + CF 网段收紧）。
- **JWT Cookie 无 `Secure` 标志**：后端以 `request.url.scheme == "https"` 判定，回源 http 恒为 false。有 `httponly + samesite=lax` 兜底。（2026-08-29 已修：新增 `COOKIE_SECURE` 配置 + `X-Forwarded-Proto` 兜底判定，生产 `.env` 设 `true` 即可；见 `.env.example`。）
- **PV 异常峰值（✅ 已定性，勿再误诊为刷量）**：2026-08-22/23 出现 292 万 / 189 万 PV 峰值（正常日约 0.9~3 万），`GET /stats/visits` 的 `total`（487 万）约 99% 来自这两天。**经站长确认：根因是统计方法 bug，不是脚本刷量；统计口径已改正（2026-08）**，`total` 失真是 bug 的结果而非滥用证据。
  - **教训**：以后看到 PV 尖峰，第一步先核对统计口径本身（打点触发次数、聚合/累加逻辑、去重规则），确认统计方法无 bug 之后再考虑滥用；限流可绕过（见下条 XFF 问题）是独立的加固项，不能作为「被刷了」的证据。

## 11. 前端类型检查双门槛：`vue-tsc --noEmit` 是弱检查，`npm run build`（`vue-tsc -b`）才是真门槛

- **现象**：本地 `npm run typecheck`（`vue-tsc --noEmit`）通过，推上服务器后 Docker 构建 `npm run build` 报 TS 错误（TS2538 `Type 'undefined' cannot be used as an index type`，`mock.ts` 里拿可空的 `demo_type` 直接做索引键），前端镜像构建失败。
- **根因**：`frontend/tsconfig.json` 是 **solution 式**文件——`"files": []` + 只有 `references` 指向 `tsconfig.app.json` / `tsconfig.node.json`。`vue-tsc --noEmit` 不带 `-b` 时只检查 solution 根（没有任何文件）→ **近乎空跑**；而 `npm run build` = `vue-tsc -b && vite build`，`-b` 才会沿 references 真正逐项目检查。两个命令的检查强度完全不同，`typecheck` 绿 ≠ 构建能过。
- **修复**：`mock.ts` 的 `demos_by_type` reduce 前先 `const t = d.demo_type || 'web'` 判空（commit `3295a1d`）。
- **预防**：
  1. 本地验证**一律用 `npm run build`**——与 Dockerfile 内逐字相同的命令，过了它等于过了服务器那关；`typecheck` 脚本只能当快速参考，不可作为发布门槛。
  2. 涉及 TS 类型收窄的写法（可空字段做索引键、`arr[0].x` 无判空等）按 `-b` 模式的严格度写，别按 `--noEmit` 的体感写。
  3. 以后若想修 `typecheck` 脚本本身，可改为 `vue-tsc -b`（改完先跑一次真实构建确认 composite 配置兼容）。
- **关联教训**：与 §4.1「本地验证要用客户端真实路径」同源——**验证环境与发布环境不一致 = 检查等于没做**。

## 12. astra 橱窗本地预览：三连环坑（Vite blocked-host / changeOrigin / fetch 改不了 Host）

橱窗按 Host 头分视区（见 [astra橱窗分离.md](./astra橱窗分离.md)），本地跑通踩了三个连在一起的坑，逐个记：

- **坑 A · Vite dev 403 blocked host**：hosts 加好 `astrademos.top`、`vite` 也 `host:true`，访问 `http://astrademos.top:5173` 却 403 `Blocked request. This host is not allowed`。
  - **根因**：Vite 6+（本项目 8.2.1）新增 dev server 主机白名单，非 localhost/127 的 Host 一律拒。
  - **修复**：`vite.config.ts` → `server.allowedHosts: ['astrademos.top', '.astrademos.top']`（commit `7b11fe7`）。生产 nginx 不受此管，只影响 dev。
- **坑 B · 代理把 Host 洗成 localhost**：加了 allowedHosts 后页面能开，但橱窗里数据还是主站全量（`fun_mode=false`、有论坛数字）。
  - **根因**：`changeOrigin:true`（默认常见写法）会把转发给后端的 Host **改写成 target host**（`localhost:8000`）→ 后端 `resolve_scope` 永远判成 deep 视区。
  - **修复**：`/api|/preview|/media` 三个 proxy 全改 `changeOrigin:false`，原始 Host 才能透传。主站 localhost 访问不受影响（Host 本就是 localhost，仍判 deep）。
- **坑 C · `node fetch()` 冒烟测试假失败**：用 `fetch(url,{headers:{Host:'astrademos.top'}})` 写脚本测门禁，结果 `/docs` 仍 200、橱窗池仍返回全量——一度以为后端 middleware 没生效。
  - **根因**：`Host` 是 fetch 规范的 **forbidden header**，浏览器/undici 静默丢弃自定义值，实际发的是 URL 派生的 `127.0.0.1:8000`。
  - **修复**：脚本冒烟改用 `node:http` 裸请求（`http.request({headers:{Host:...}})` 可正常设）或 `curl --resolve`；pytest 侧用 `TestClient(app, base_url="http://astrademos.top")`（httpx 会真实下发 Host 头，无此坑，已落 `test_scope.py`）。
- **预防**：凡「按 Host/Origin 头分流」的功能，验证必须用**能真正控制该头**的客户端；fetch/浏览器地址栏改不了的头，别拿来当测试手段。与 §9「模块级 global」、§11「双门槛」同属**验证手段与被测机制不匹配 → 假信号**一族。

## 13. `autoflush=False` + relationship 读未提交行：模型实体静默漏挂（v2 B1，2026-08-31）

- **现象**：v2 双写链路里**只有「第一次」上传能挂上 Model 实体**，之后同样带 `model:xxx` 标签的作品，`GET /demos/{slug}` 的 `models[]` 恒为 `[]`。接口全程 201/200、日志零报错，`demo_models` 表就是不涨。
- **根因**（三个条件叠齐才炸）：
  1. `database.py` 的 `SessionLocal(autoflush=False)`（为防「查询触发意外 flush」而关，这次反成祸根）；
  2. `_set_demo_tags()` 里 `db.add(DemoTag(...))` 后**没有 flush**，直接调 `sync_demo_models()`；
  3. `sync_demo_models()` 靠 `demo.tag_associations` **懒加载**读标签集合 → 真发一条 SELECT 查库 → 未落库的 pending 行查不到 → `values` 为空 → 一条 `demo_models` 都不写。
- **为什么「第一次」是对的（最阴的地方）**：首次上传时 `author:public` 等标签**尚不存在**，`_ensure_tag()` 走 `db.add(tag) + db.flush()`，这次 flush 把**整个 session 的 pending 对象**（含刚加的 `DemoTag`）一并落库，relationship 才读得到；第二次起标签已存在 → 不再 flush → 静默漏挂。**「只在冷启动第一次正确」的逻辑，单次冒烟测试必然放过。**
- **修复**：`sync_demo_models()` 入口先 `db.flush()` 再读 relationship（`backend/app/services/model_service.py`，注释写明三条件）。放在 service 层而非某个 router，是为了覆盖全部调用方（创建 / 编辑 / 将来管理端重挂标签）。
- **预防（三条可复用）**：
  1. `autoflush=False` 的项目里，**任何「先 add、再靠 relationship 读回」的代码都是雷**——要么显式 `db.flush()`，要么把刚创建的对象**用局部变量直接传下去**，别绕道 relationship 再查一次；
  2. 双写 / 同步类逻辑的测试必须**连跑两次以上**（第二次才是常态路径）：本次新增的 `test_repeated_upload_reuses_model_entity` 是唯一能抓到它的用例；
  3. 排查「表不涨但接口全 2xx」，先怀疑**写入前是否读了旧快照**，而不是先怀疑查询条件。
- **同类**：§5.1「`create_all` 不改旧表」、§5.3「迁移函数写了没调用」——同属「代码写了但没在正确时机生效」一族。

## 15. 校验白名单写死在路由里 = 静默失效的筛选项（2026-08-31）

**症状**：审计接口 `GET /admin/audit?action=...` 的 pattern 是硬编码的：

```python
action: str | None = Query(default=None, pattern="^(create|update|...|review)$")
```

后来 `attribute` 动作上线（归属工作台），**没有报错、也没有异常**，只是 `?action=attribute` 永远返回 422、审计页下拉里永远看不到这一类记录 —— 数据一直在写，查询侧看不见。

**为什么危险**：这类脱节不会让任何测试自动变红（老用例只测自己用的动作），也不会打日志。发现路径通常是"人肉在 UI 里筛一次"。

**修法（三条一起做）**：

1. 白名单收进 `models.AUDIT_ACTIONS` 单一来源：`pattern="^(" + "|".join(AUDIT_ACTIONS) + ")$"`；
2. **允许值随响应返回**（`actions: [...]`），前端下拉用它 —— 否则同一个清单会在 TS 里再抄一份、再脱节一次；
3. 加一条**差集断言**的回归测试：拿数据库里实际出现过的 action 与常量比对，`missing = actions_in_db - set(AUDIT_ACTIONS)`，漏一个就红。

**同族坑（本仓已记过）**：`SUGGESTION_KINDS` 与 `suggestion_service._execute` 的分派分支、`RUN_META_KEYS` 与列迁移清单、astra 白名单 `ASTRA_DENY_SEGMENTS` 与新路由 —— 都是"两处清单必须同时改，忘一处就静默出错"。凡写这种清单，**当场问一句：能不能只有一处？** 不能的话，必须有一条断言把两处绑在一起测。

**同族的第二种形态：同一件事写两份实现**（不是两份清单）。本轮加「改 slug 后旧值转别名、旧链接仍可解析」时踩到：`GET /models/{slug}` 在路由里写了一遍 `Model.slug == slug`，`model_service.model_detail()` 里又写了一遍 —— 只改 service 不够，路由那份不认别名，旧链接照样 404。修法是把解析收敛成唯一入口 `_find_model(id → slug → 别名)`，路由只调它。

**推广判据**：加新行为时若发现"要在两个地方各改一次"，就说明存在第二份实现；先收敛成一处再往下做，否则每个特性都要重踩一遍。

## 16. QueuePool 被榨干 = 整站挂死且只能重启（2026-09-01）

**症状**：日志里几百行同一个栈：

```
sqlalchemy.exc.TimeoutError: QueuePool limit of size 20 overflow 20 reached,
connection timed out, timeout 30.00
    at deps.py:14 current_user → db.get(User, user_id)
INFO:app:GET /api/v1/auth/me -> 401 268544ms
```

一个"查当前登录用户"的接口跑 **268 秒**；`current_user` 是请求里第一次碰库的地方，说明 40 个连接已被别人占满，`auth/me` 只是受害者。

**雪崩机制（为什么不自愈）**：只要有少量连接被长时间占住 → 其余请求 checkout 要等满 `pool_timeout`（默认 30s）→ 单请求在飞时长从 10ms 变成 30s → 按 Little 定律「同时在飞请求数 = 到达率 × 时长」暴涨约 3000 倍 → 40 个连接全部占死 → 之后每个请求都 30s 超时 → 稳态卡在"全满"，**只能重启容器**。

所以真正的元凶往往是"某个长占"，而把事故放大成全站挂死的是"30s 等待 + 40 容量"这个组合。

**本次确认的 4 个长占/放大点（已全部修）**：

| # | 位置 | 问题 | 修法 |
|---|---|---|---|
| 1 | `services/oss_sync.py` | 会话跨越整个上传循环才 close（每 demo 一次 HEAD + 全量上传，分钟级）；而且**每次容器启动都自动跑** | 只借连接取 slug 清单，`with SessionLocal()` 取完立刻归还，再做网络 I/O |
| 2 | `services/scope.py` 预览门禁 | 缓存**没有 single-flight**：一个 demo 页并发拉 N 个子资源，在 TTL 过期瞬间会同时 checkout N 个连接；预览又是全站最大流量 | 按 slug 加锁（同 slug 只有一个线程查库，其余吃缓存）+ TTL 60s→300s + 查库异常时 deep 放行/astra 拒绝 |
| 3 | `services/site_info_service.py` | 首屏必打的聚合接口，TTL 一到 N 个并发各自跑十几条查询（含 forum_replies 全表扫）；且内部还嵌套 `visits.get_stats()` 再开第 2、第 3 个会话 | stale-while-revalidate（只放一个线程回源，其余吃旧值）+ `visits.get_stats(db)/get_live_stats(db)` 复用调用方会话 |
| 4 | `database.py` | `pool_timeout` 用默认 30s → 进入上面的雪崩且无法自愈 | `pool_timeout=5`：宁可快速 500，让流量退去后自动恢复 |

另外 `services/oss.py` 的 `_bucket()` 没设超时，oss2 默认 60s —— OSS 侧网络异常时一次 HEAD 能拖一分钟，现已统一 `connect_timeout=10`。

**仍存的已知模式（下次继续清）**：`forum.py` / `demos.py` / `admin.py` / `community_service.py` 里，请求已持有 `get_db` 会话后又调 `notification_service.create()` 开**第二个**会话（嵌套 checkout）。因为通知在 `db.commit()` 之后且吞异常，所以现在最坏只是白等 5s，不再挂死；但正确解法是让通知服务**复用请求会话**（签名改成 `create(db, ...)`）。

**排查套路（下次卡住先别重启）**：

```bash
# 1) 看池子状态：checkedout 多少、是不是满 40 且不回落
docker compose exec backend python -c "from app.database import engine; print(engine.pool.status())"
# 2) 谁在打：按路径统计请求量与耗时（找长占与 fan-out）
docker compose logs --tail 500 backend | grep "INFO:app" | awk '{print $2, $3}' | sort | uniq -c | sort -rn | head
# 3) 同步任务是否正在跑（它会长时间传 OSS）
docker compose logs --tail 300 backend | grep "oss-sync"
```

**教训一句话**：连接池饱和不是"慢"，是"死锁"。任何**跨网络 I/O 持有会话**的代码（上传/下载/subprocess/第三方 API）都是定时炸弹，必须"先取数据、立刻还连接、再干活"。

## 17. `pageKey` 用 `fullPath` = 每次改 query 都整页重挂（2026-09-02）

**症状**：模型页点「再显示 24 件」看似无反应、只是回到顶部；决策人一句「又是所有变化都会使页面到最顶」。

**根因**：`App.vue` 用 `<component :key="pageKey">`，而 `pageKey` 对非 keepAlive 页面取 `route.fullPath`。
于是**任何 query 变化都被当成换页** —— 组件卸载重挂：滚动归零、已填内容丢失、请求重发。
我先只改了 `scrollBehavior`（同 path 返回 `false`），复测仍然弹顶 —— 那只是下游症状，真凶是重挂。

**修法**：`pageKey = keepAlive ? name : (meta.remountOnQuery ? fullPath : path)`，
并给每个「依赖 query」的视图补自己的 watch（`DemosView` / `ForumListView` / `AdminView`）。

**两个必须一起记住的约束**：

1. 自写 query 的页面，其「应用 query」函数**必须幂等** —— 否则自家写入会被自己的 watch 当成新导航再触发一次（`DemosView.applyRouteQuery()` 靠返回值决定是否 reset）。
2. 少数页面的身份**就是** query（`/upload?slug=x` 换参数＝换作品），这类必须显式标 `meta.remountOnQuery` 保留重挂，否则会拿着上一件作品的表单去编辑另一件。

**教训一句话**：`key` 决定组件生命周期；拿 URL 当 key 等于拿「地址栏字符串」当「页面身份」—— 二者不等价。

## 18. 「接口 200」不等于「用户看到的对」：验证必须在重启服务之后（2026-09-02）

**症状**：我上一轮声称分页端点已验证，实际打开模型页是整页 `Not Found`。

**根因**：演示后端进程是在我**加路由之前**启动的。我用 curl 打的是另一个新起的临时进程（200），
浏览器用的是旧进程（404）。两边都「测过」，结论却是假的。

**修法（已固化成脚本）**：CDP 驱动 headless Edge —— 同源 `fetch` 登录拿 cookie → 逐页导航 →
**注入 CSS 关掉动画**（否则卡片正淡入，看不出真实视觉）→ 截图 + `Runtime.evaluate` 做结构断言。
断言要写「点击前后 scrollY 不变」「卡片 12→36」这种**可失败的**判据，而不是肉眼看「好像多了」。

**顺带抓到的同类问题**：论坛回复列表原本必须先选主题（上百主题选不过来）；
合并后的旧写法会把作品静默挂到已退役实体上（序列化过滤 → 看起来"没有模型"）—— 都是"接口在、路径没走通"的形态。

**教训一句话**：改完后端代码 = 必须重启服务再验；声称"验过"之前，先问一句"验的是哪个进程"。

## 19. 两个"看起来是 UI 问题、其实是机制失效"的 bug（2026-09-02）

### 19.1 索引失效从未生效：自己和自己比较

```python
def bump_task_index(): _idx["version"] += 1          # 写路径
def index_version():   return _idx["version"]        # 调用方读同一个值
def _ensure_index(db, version):
    fresh = ... and _idx["version"] == version       # ⇒ 恒真，永远不重建
```

写路径"以为"自己失效了，读路径"以为"自己最新，**注释也写着主动失效** —— 但唯一真正生效的是 300s TTL。
症状是"新建的题目搜不到"，很容易被误判成"算法不行/语料不够"。

**教训**：失效机制必须让"数据代数"和"索引已构建到哪一代"**分开记录**；
写完后立刻读一次并断言能读到新数据 —— 这条断言（`test_write_path_actually_invalidates_index`）才是防线。

### 19.2 字典少一个键崩掉整页：`stepProblems[4]` 不存在

向导有 4 步，`stepProblems` 只写了 `1/2/3`；模板 `stepProblems[step].length` 一进第 4 步就抛
`TypeError` → **渲染崩溃、页面卡死、无法提交**。症状像"下一步按钮坏了"，很容易去改按钮。

**教训**：任何"按索引取集合再取属性"的模板表达式都要 `?.` / `?? 0` 兜底；
并且**新增一步必须走一遍到提交**，不能只截前三步的图。

### 19.3 测试侧三个陷阱（同一轮全踩了一遍）

1. **`v-show` 让"存在"≠"可见"**：断言 `!!document.querySelector('.uw-task')` 永远为真，
   即使它在隐藏的步骤里。必须验 `offsetParent !== null`。
2. **裸 `fetch` 读 admin 接口**：脚本没带会话 cookie → 401 → 字段 undefined → 断言恒为 0，
   看起来"没生效"。要么在页面里 fetch（同源带 cookie），要么显式带凭据。
3. **不假设接口返回顺序**：`items[len-1]` 不是"最新"；按业务键（标题/id）找。
   另外同一测试文件里 `_upload` 用了**固定文件体** → 内容去重让后一个用例 409，
   表现为"隔离跑通过、全套失败"。

## 20. 读路径上的写事务：`database is locked` 500 + 预览缓存被打穿（2026-09-03）

**症状**：`GET /api/v1/demos/{slug}` 偶发 500，日志：

```
sqlite3.OperationalError: database is locked
  File "/app/app/routers/demos.py", line 355, in get_demo → db.commit()
```

同时一批 `POST /stats/heartbeat -> 200 4995ms / 4672ms / 4671ms` —— 4.6~5.0s 正是
`busy_timeout=5000` 的形状，整站在为写锁排队。

**根因链（三个独立问题叠在一起）**：

1. `get_demo` 里 `demo.view_count += 1; db.commit()` —— **每次浏览都是一次写事务**。
   SQLite 单写者，写队列一长就 `database is locked`，把详情页打成 500。
2. `Demo.updated_at` 带 `onupdate=utcnow` → 任何对 demo 行的 UPDATE（浏览/下载/评分/审核）
   都会顺手刷新它。
3. 版本化预览 URL 的版本 key 取自 `updated_at` → **每次浏览都换新 URL** →
   `<base href="/preview/{slug}/v{新版本}/">` 让所有子资源也换新 URL →
   CDN/浏览器缓存命中率归零，全站预览流量全部回源（`docker stats` 里 backend NET ↑12.6GB）。

**修法**：

| # | 改动 | 作用 |
|---|---|---|
| 1 | 新增 `services/counters.py`：浏览/下载/主题浏览计数**内存批次 + 30s 落库**（原子 `UPDATE ... SET count = count + :n`） | 读路径零写事务，写风暴消失 |
| 2 | `get_demo` / `download_demo` / `forum.get_topic` 改用 `counters.bump()`，**不再 commit** | 详情页/下载/主题页不再可能因计数 500 |
| 3 | `Demo.updated_at` 去掉 `onupdate=utcnow`，只在 `update_demo` 显式赋值 | `updated_at` 回归"内容被改过"语义 |
| 4 | 版本 key 改用 `content_hash[:12]`（无 hash 退 `created_at`） | 版本只随内容变化，CDN 缓存恢复 |

**教训**：

1. **读路径上永远不要写库**。PV/下载这类统计计数，一律内存批次 + 定时落库
   （`visits.py` 早有同款模式，这次只是没抄）。
2. **改缓存策略前，先查"这个字段还会被谁写"**。`updated_at` 带 `onupdate` 时
   它不等于"内容版本"，等于"最后被碰过"——拿它当版本 key 是定时炸弹。
3. **统计计数失败绝不能 500 业务页**。计数是"尽力而为"语义，落库失败只该打 warning。
4. 排查"偶发 500 + 一堆 4.6~5.0s 慢请求"时，先看 `busy_timeout` 的值——
   慢请求时长贴着它，就是写锁排队，不是慢查询。
